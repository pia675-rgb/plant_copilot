# Plant Maintenance Copilot

**팀 Plant Copilot Lab** · AI Solution 리그

플랜트 계장 설비의 고장 알람을, **벤더 매뉴얼과 현장 보수 이력 양쪽에 대조해서** 답하는 정비 보조 도구입니다.
근거를 찾지 못하면 답을 지어내지 않고 거절합니다.
그리고 인터락은 표로 읽는 대신 **조건을 눌러 동작을 재현해볼 수 있습니다.**

## 1. 어떤 문제를 풀려고 했나

### 1-1. 진짜 시간을 잡아먹는 알람은 따로 있다

현장 알람은 두 종류입니다.

**공정 알람** (HH ALARM, LL ALARM 등) — 값이 범위를 벗어난 것이고, 무엇을 봐야 하는지 명확합니다. 숙련자는 몇 분 안에 처리합니다.

**진단 알람** (LOOP ERROR, PLC MODULE FAULT, Wire break 등) — 설비가 스스로 고장을 신고한 것입니다. 이건 다릅니다. 원인이 배선인지, 계기인지, 카드인지, 설정인지 알 수 없습니다. 매뉴얼을 뒤져도 일반론만 나옵니다. 결국 **벤더에 문의하고 답을 기다립니다.**

이 도구가 겨냥하는 건 두 번째입니다.

### 1-2. 대기시간은 왕복 횟수만큼 곱해진다

Siemens 기술문의는 답변을 받기까지 **짧아도 2~3일**이 걸립니다. 그리고 이건 한 번으로 끝나지 않습니다.

문의서에 정보가 부족하면 되묻습니다. 어느 랙 어느 슬롯인지, 진단 버퍼에 무엇이 찍혔는지, 그 채널에 무엇이 물려 있는지, 리던던시 상태는 어땠는지. **현재 왕복은 평균 2~3회**입니다.

```
총 소요 = 자체 판별 + (왕복 횟수 × 2~3일) + 조치
```

왕복이 3회면 대기만 6~9일입니다. 문제는 대기 자체가 아니라 **왕복 횟수**입니다.

### 1-3. 답을 아는데 꺼내지 못한다

그런데 이 알람들은 대개 **처음 보는 게 아닙니다.**

IO 카드에는 수명이 있습니다. 그래서 특정 시기가 되면 같은 계열 모듈에서 같은 고장이 몰려서 나옵니다. 지난달에 옆 라인에서 똑같은 걸 겪었고, 그때 원인이 무엇이었는지 담당자는 기억합니다.

**그 기억이 문서로 남아 있지 않을 뿐입니다.**

그래서 매번 처음부터 다시 시작합니다. 매뉴얼을 다시 뒤지고, 벤더에 다시 묻고, 다시 사흘을 기다립니다.

### 1-4. 그리고 매뉴얼이 항상 맞는 것도 아니다

벤더 매뉴얼은 일반적인 경우를 씁니다. 현장은 그 배관, 그 판넬, 그 배선의 사정이 있습니다.

실제 사례 하나입니다.

> **증상** — 채널 단선 진단 (Wire break)
> **매뉴얼대로** — 배선 점검. 이상 없음
> **실제 원인** — 미사용 채널이 Disable 처리되지 않아 단선으로 진단됨
> **조치** — 미사용 채널 Disable

매뉴얼만 따랐으면 배선을 계속 뜯어봤을 겁니다. 이런 **매뉴얼과 현장의 불일치**가 보수 이력에서 확인됩니다.

### 1-5. 문서는 다섯 종류로 흩어져 있다

알람 하나를 판단하려면 이만큼을 봐야 합니다.

| 알고 싶은 것 | 봐야 하는 문서 |
|---|---|
| 어느 판넬 어느 카드 어느 채널인가 | IO List |
| 어느 회사 무슨 모델인가 | Instrument List |
| 어느 단자에 물려 있나 | TB List |
| 이 알람이 무슨 뜻인가 | 벤더 매뉴얼 (영문 PDF 수백 쪽) |
| 이걸 멈추면 뭐가 같이 서나 | Interlock List |
| 도면 어디에 있나 | P&ID · 배치도 |

문서마다 태그 표기가 다릅니다. 숙련자는 머릿속으로 잇지만, **그 연결은 어디에도 문서화되어 있지 않습니다.**

## 2. 목표 수준

프로토타입이 도달하려는 지점을 숫자로 정의했습니다.

| 항목 | 목표 | 근거 |
|---|---|---|
| 태그 하나로 5문서 연계 조회 | 6종 문서 전부 | 판단에 필요한 문서가 6종 |
| 인터락 조회 정확도 | 100% | 오답이 안전에 직결되므로 부분 정답을 허용하지 않음 |
| 판넬·카드 조회 정확도 | 100% | 위와 동일 |
| 이력 매칭 정확도 | 100% | 남의 계기 이력이 새면 잘못된 방향으로 조치가 흘러감 |
| 이력 기능의 검색 비의존 | 검색 전면 실패 시에도 동작 | 검색 정확도에 이력을 종속시키면 코드표를 못 집는 순간 기능 전체가 죽음 |
| 근거 없는 질의 거절률 | 100% | 지어낸 답 1건이 도구 전체의 신뢰를 무너뜨림 |
| 한글 질의 → 영문 매뉴얼 검색 | 수동 번역 사전 없이 | 현장 질의는 한글, 매뉴얼은 영문 |
| 답변당 근거 표시 | 문서명 + 페이지 + 이력 매칭 근거 | 근거를 못 대면 현장에서 못 씁니다 |

**정확도 목표를 100%로 잡은 이유**는 이 도구가 안전 판단에 개입하기 때문입니다. 인터락을 90% 맞히는 도구는 쓸 수 없습니다. 나머지 10%가 어느 것인지 모르기 때문입니다. 그래서 **맞히거나, 모른다고 말하거나** 둘 중 하나만 하도록 설계했습니다.

## 3. 기대 성과

### 3-1. 세 갈래로 나뉩니다

**1단 — 이력에 유사 사례가 있는 경우: 문의 없이 종결**

가장 큰 절감입니다. 2~3일 대기가 통째로 사라집니다. 모듈 수명에서 오는 재발성 고장이 많아, 이 경로에 해당하는 비율이 낮지 않습니다.

**2단 — 이력에 없는 경우: 문의 1회로 종결**

태그 하나로 판넬·슬롯·채널·인터락 영향·도면 위치가 한 번에 나옵니다. 문의서에 들어갈 항목이 처음부터 완비되므로 되물음이 사라집니다. **왕복 2~3회가 1회로** 줄면 대기가 4~9일에서 2~3일이 됩니다.

**3단 — 근거가 부족한 경우: 거절**

억지 답변으로 잘못된 방향에 하루를 쓰는 것을 막습니다. 이것도 절감입니다.

### 3-2. 부수 효과 — 사후 대응에서 계획으로

이력에 날짜와 태그가 쌓이면 **모듈 교체 시기를 예측할 수 있습니다.**

IO 카드 수명이 특정 시기에 몰린 고장으로 나타난다면, 그 패턴은 이력에서 보입니다. 고장 나고 대응하는 방식에서, 고장 나기 전에 교체 계획을 세우는 방식으로 넘어갈 수 있습니다.

## 4. 어떻게 푸는가

### 4-1. 태그 하나로 6문서를 잇습니다

태그를 입력하면 IO List · Instrument List · TB List · Interlock List · 벤더 매뉴얼 · 도면이 한 화면에 붙습니다. 그리고 답변마다 **어느 문서 몇 쪽에서 나왔는지**를 함께 냅니다.

### 4-2. 매뉴얼과 현장 이력을 나란히 놓습니다

이 도구의 핵심 화면입니다. 왼쪽이 매뉴얼 근거, 오른쪽이 현장 보수 이력입니다.

각 이력에는 **매뉴얼과의 일치 여부**가 표시됩니다. 불일치 이력이 있으면 화면에 경고가 뜹니다.

> 현장 이력이 매뉴얼과 다른 원인을 기록한 사례가 있습니다.

**이 한 줄이 이 도구의 존재 이유입니다.** 문서 검색기는 매뉴얼이 틀렸다고 말하지 못합니다.

### 4-3. 이력을 목록이 아니라 판단 근거로 올립니다

이력을 옆에 늘어놓기만 하면 결국 사람이 다시 읽어야 합니다. 그래서 조치 순서 **맨 앞에** 이력 카드를 세우고, **매뉴얼대로 했는데 아니었던 기록을 매뉴얼 근거보다 먼저** 보여줍니다.

무엇을 올릴지는 세 갈래로 결정합니다.

| 단계 | 조건 | 뜻 |
|---|---|---|
| L1 | 같은 태그 · 증상 유사 | 이 계기에서 이 증상이 재발 |
| L2 | 같은 태그 · 증상 무관 | 이 계기의 다른 이력 |
| L3 | 같은 기종 다른 태그 · 증상 유사 | 같은 기종 다른 계기의 동일 증상 |

**세 단계 모두 검색 결과를 필요로 하지 않습니다.** 알람 코드를 매칭의 축으로 삼으면 검색이 코드표를 집지 못하는 순간 이력 기능 전체가 죽습니다. 태그·증상·기종만으로 결정하므로 **검색이 실패해도 이력은 남습니다.**

그리고 각 이력마다 **왜 올라왔는지**를 함께 표시합니다. L3(다른 계기의 기록)가 올라왔는데 이유가 안 보이면 사용자가 신뢰하지 못합니다.

```
[H1] 2025-04-08 · PIT-1010 · 채널 단선 진단 (Wire break)
     매뉴얼 대조: 불일치
     처음 조치: 배선 점검 (이상 없음)
     실제 원인: 미사용 채널이 Disable 되지 않아 단선으로 진단됨
     최종 조치: 미사용 채널 Disable 처리 · 40분 · 담당 P.C.
     매칭 근거: L1 (동일 태그 · 증상 일치)
```

**원문을 그대로 옮기며 요약하지 않습니다.** 요약하는 순간 근거가 아니라 생성물이 됩니다.

카드는 규칙으로 결정하고, LLM은 그 뒤에 문장만 다듬습니다. 실제로 `AIT-4002` 조회에서 LLM이 만든 첫 조치는 매뉴얼이 지시하는 카트리지 교체가 아니라 `[H1]`을 인용한 에어락 확인이었습니다. 매뉴얼 조치는 두 번째로 밀렸습니다.

### 4-4. 근거가 없으면 거절합니다

검색 결과의 충분성을 규칙으로 채점하고, 기준에 못 미치면 질의를 다시 써서 재검색합니다. 그래도 부족하면 `abstain` — 모르겠다고 답합니다.

그럴듯한 문장을 만들어내는 것보다 **못 찾았다고 말하는 편이 현장에서 안전합니다.**

### 4-5. 인터락을 표가 아니라 움직이는 화면으로 확인합니다

인터락 리스트는 표입니다. 표를 읽어서 "이 펌프가 왜 안 도는지"를 파악하려면 조건 대여섯 개를 머릿속에서 조합해야 합니다. 그리고 조합해봐야 **맞는지 확인할 방법이 없습니다.**

확인하려면 실제로 조건을 만들어봐야 합니다. 밸브를 닫아보고, 레벨을 떨어뜨려보고, 트립을 걸어봐야 합니다. 시운전 중이면 위험하고, 운전 중이면 아예 불가능합니다.

이 도구는 그 확인을 **화면에서 하게 합니다.**

현업에서 작화 엔지니어가 P&ID를 보고 SCADA 화면을 그리는 것과 같은 방식으로, 조건을 공정 그래픽 위의 뱃지로 배치했습니다. **뱃지를 눌러 조건 상태를 바꾸면 인터락이 실제로 걸리고 풀립니다.**

무엇이 확인되는지가 중요합니다.

**어느 조건 하나가 막고 있는지** — 기동 허가 조건이 넷인데 셋만 충족된 상황을 만들어보면, 남은 하나가 무엇인지 화면에서 바로 짚힙니다.

**래치인지 자동 복귀인지** — 표로는 구분되지 않는 지점입니다. 정지 인터락(과부하·E-STOP·VFD Fault)은 조건이 해소돼도 **리셋을 눌러야** 풀립니다. 반면 저수위 자동 정지는 레벨이 회복되면 **저절로** 풀립니다. 화면에서는 이 차이가 즉시 보입니다. 현장에서 "왜 조건이 정상인데 안 도느냐"는 혼동이 가장 자주 생기는 대목입니다.

**리스트 자체의 모순** — 조건을 이리저리 바꿔보다 보면 어떤 조합으로도 기동이 안 되는 상태가 드러나기도 합니다. 인터락 리스트 검토 단계에서 발견하면 시운전에서 겪지 않아도 되는 문제입니다.

그리고 이건 **교육 도구이기도 합니다.** 신규 인력이나 협력사 엔지니어에게 인터락을 설명할 때, 표를 놓고 말로 설명하는 것과 눌러보게 하는 것은 이해 속도가 다릅니다.

## 5. 기존 방식과 무엇이 다른가

| | 문서 검색 도구 | 일반 LLM 챗봇 | 이 도구 |
|---|---|---|---|
| 답의 출처 | 문서 | 모델 내부 | 문서 + **현장 이력** |
| 근거 제시 | 문서 링크 | 없거나 부정확 | 문서명 + 페이지 + 이력 WO 번호 |
| 모를 때 | 무관한 결과 나열 | 그럴듯하게 지어냄 | **거절** |
| 매뉴얼이 틀렸을 때 | 알 수 없음 | 알 수 없음 | **불일치로 표시** |
| 안전 판단 | 불가 | 불가 | 인터락 조회 정확도 100% |
| 인터락 확인 방법 | 표를 읽음 | 표를 요약해줌 | **조건을 눌러 동작을 재현** |

**결정적 차이는 세 번째, 네 번째, 다섯 번째 행입니다.** 모른다고 말할 수 있고, 매뉴얼이 틀렸다고 말할 수 있고, 인터락을 읽는 게 아니라 **움직여볼 수 있는** 것.

앞의 둘은 답변의 신뢰에 관한 것이고, 마지막 하나는 **문서를 읽는 일을 조작해보는 일로 바꾼 것**입니다. 검색 도구와 시뮬레이터의 차이입니다.

## 6. AI 네이티브 설계

### 6-1. LLM을 마지막 단계에만 씁니다

검색 · 판정 · 인터락 조회 · 판넬 조회는 **전부 규칙과 색인으로** 처리합니다. LLM은 이미 찾아낸 근거를 조치 순서로 정리할 때만 관여하고, 생성된 조치가 실제 근거 ID를 참조하는지 검증합니다.

안전에 직결되는 판단을 확률적 생성에 맡기지 않기 위해서입니다.

이력 카드가 그 경계를 보여줍니다. **어떤 이력을 올릴지와 어떤 순서로 세울지는 규칙이 정하고, LLM은 그 뒤에 문장만 다듬습니다.** LLM이 프롬프트의 지시를 놓쳐도 카드는 살아 있습니다. 그리고 LLM이 만든 각 단계가 실제 근거 번호(`[1]`)나 이력 번호(`[H1]`)를 인용하는지 검증하고, 없는 번호를 인용한 단계는 코드에서 버립니다.

### 6-2. 임베딩이 번역 사전을 대체합니다

현장 질의는 한글이고 벤더 매뉴얼은 영문입니다. 기존 방식은 용어 대조표를 사람이 만들어야 했습니다.

다국어 임베딩(`bge-m3`)으로 이 단계를 없앴습니다. **수동 사전 없이** 한글 질의가 영문 매뉴얼 본문에 붙습니다. 임베딩 제공자를 바꿔 측정한 결과, 이 한글→영문 구간이 다국어 임베딩 없이는 무너진다는 것을 확인했습니다.

### 6-3. LangGraph로 검색-채점-재질의 루프를 구성

한 번 검색해서 끝내지 않습니다. 결과가 충분한지 채점하고, 부족하면 질의를 다시 써서 재검색하고, 그래도 부족하면 거절합니다. 이 판단 흐름 자체가 그래프로 구현되어 있습니다.

## 7. 무엇으로 확인했나

상세는 `3_검증결과` 폴더에 있습니다. 요약만 적습니다.

| 항목 | 문항 | 결과 |
|---|---|---|
| 인터락 조회 (층 분리 · 역방향 · 부재 판정 · 원문 보존) | 67 | 67/67 |
| 판넬 · 카드 조회 (위치 · 카드 · 채널 · 상실 영향) | 211 | 211/211 |
| 이력 우선 (3단 매칭 · 정렬 · 기종 가드) | 100 | 100/100 |
| 전 경로 고장 주입 (`selfcheck`) | 40 | 40/40 |
| 종합 평가셋 (검색 구성 · 임베딩 비교) | 45 | 아래 §7-1 · §7-2 |

**부정 문항을 함께 넣었습니다.** 나와야 할 것이 나오는지만 재면 규칙이 과하게 넓어도 만점이 나옵니다. 이력 100문항 중 11문항이 "나오면 안 되는 것이 안 나오는가" 를 봅니다.

### 7-1. 검색 구성 비교 — 무엇이 점수를 만드는가

같은 색인(1,210청크), 같은 평가셋(45문항)에서 검색 구성만 바꿔 측정했습니다.

| 구성 | 전체 | code | **syn (한글→영문)** | en | body | typo |
|---|---|---|---|---|---|---|
| lexical (BM25만) | 16/45 | 4/4 | **0/14** | 4/5 | 0/9 | 0/4 |
| **hybrid (배포 구성)** | **28/45** | 4/4 | **8/14** | 4/5 | 5/9 | 1/4 |
| **full (로컬 최고 구성)** | **31/45** | 4/4 | **9/14** | 5/5 | 5/9 | 2/4 |

**대표 수치를 둘 다 싣습니다.** 공개 URL은 `hybrid` 고정이므로 심사위원이 직접 사용하실 때의 값은 **28/45**입니다. `full`은 cross-encoder 리랭커를 추가한 구성으로 **31/45**이며, 로컬에서만 동작합니다.

리랭커를 배포에서 뺀 것은 성능이 아니라 비용 판단입니다. 3점(6.7%p)을 얻는 대신 이미지에 torch 약 2GB가 들어오고 호스팅 요건이 512MB급에서 4GB급으로 올라갑니다. **얻는 것과 드는 것을 재고 고른 결과이며, 되돌릴 수 있도록 코드에는 `full` 경로를 남겨 두었습니다.**

> 이 판단은 한 번 틀렸다가 바로잡은 것입니다. 처음 측정에서는 리랭커의 기여가 0으로 나왔는데, 리랭커가 `full` 모드에서만 동작하는 것을 모른 채 `hybrid`에서 켜고 껐기 때문이었습니다. 설정값은 갈렸으나 코드가 그 분기를 타지 않았습니다. 경위는 `4_제작과정` 개발 일지 8/24에 적었습니다.

**`lexical` 0/14가 이 프로젝트의 출발점입니다.** BM25만으로는 한글 질의가 영문 매뉴얼에 한 건도 닿지 않습니다.

### 7-2. 임베딩 제공자 비교 — 핵심 기능이 무엇인지 숫자로

같은 색인, 같은 평가셋, 리랭커 off 조건에서 임베딩만 바꿔 측정했습니다.

| 임베딩 | 전체 | code | **syn (한글→영문)** | en (영문→영문) | body |
|---|---|---|---|---|---|
| bge-m3 (다국어) | 28/45 | 4/4 | **8/14** | 4/5 | 5/9 |
| openai/3-large | 21/45 | 4/4 | **3/14** | 4/5 | 1/9 |
| openai/3-small | 18/45 | 4/4 | **1/14** | 4/5 | 0/9 |

**en(영문 질의)은 세 구성이 모두 4/5로 같은데 syn만 8 → 3 → 1로 무너집니다.** 원인이 한글→영문 구간에 있다는 것이 분리되어 드러납니다. 모델 크기 문제가 아니라 훈련 목표의 차이입니다.

배포 편의를 위해 임베딩을 바꿔 보았다가 핵심 기능이 무너지는 것을 확인하고, bge-m3를 API로 제공하는 곳을 찾아 배포 방식을 다시 짰습니다.

### 7-3. 점수가 허수가 아님을 확인

**단순 통과 검사가 아닙니다.** `selfcheck`는 고장 주입 검사입니다. 태그를 몰래 바꿔치기하거나 파일을 지운 상태를 만들어, 도구가 그것을 알아채는지 확인합니다. 알아채지 못하면 실패로 처리합니다.

**변이 시험** — 기능을 하나씩 꺼서 해당 문항만 무너지는지 봅니다. 이력 규칙 100문항 기준입니다.

| 변이 | 합계 | 무너진 유형 |
|---|---|---|
| 기준 | 100/100 | — |
| 기종 조건 제거 | 89/100 | 기종 가드 · 누출 방지 문항 |
| 불일치 우선 정렬 제거 | 99/100 | 정렬 문항만 |
| 증상 유사도 무시 | 16/100 | 대부분 |

정렬을 껐을 때 정렬 문항 하나만 틀리는 것이 중요합니다. 정렬은 수집 범위를 바꾸지 않으므로 다른 유형에 영향이 없어야 맞습니다.

**자료에 없는 상황도 잽니다.** 현재 이력에는 "기종이 다른데 증상이 비슷한" 쌍이 없습니다(교차 기종 쌍 최대 유사도 0.125, 임계 0.35). 그래서 기종 조건을 지워도 실데이터 문항은 하나도 안 무너집니다. 규칙을 안 재고 있는 상태였으므로 합성 픽스처를 만들어 채웠습니다.

### 7-4. 실사용 유사 조건 검증

데모 데이터 외에 실제 프로젝트 규모의 자료로 구동해 확인했습니다.

| | 데모 자료 | 실물 자료 |
|---|---|---|
| IO 점 | 100 | 718 |
| P&ID 기기 | 100 | 505 |
| IO 카드 | 36장 | 22장 |
| 계기 리스트 | 1통 | 종류별 12통 |

실물 자료는 반출 금지 대상이므로 제출물에는 포함하지 않고, 구동 결과만 기록했습니다. 실물 계기 리스트는 계기 종류별로 여러 통으로 들어오는 것이 실제 형태여서, 파서가 그 형태를 다루는지도 `selfcheck` 항목으로 두었습니다.

## 8. 확인된 한계

숨기지 않고 적습니다.

- 도면 태그 검색은 PDF에 텍스트 레이어가 있어야 합니다. **스캔 도면은 인식하지 못합니다.**
- 조치 순서 생성 품질은 붙이는 LLM 크기에 좌우됩니다. 3B 모델에서는 문장이 거칠어집니다.
- Instrument List에 사양이 없는 태그(상태 접점 등)는 벤더 매뉴얼을 특정하지 못합니다.
- Interlock List 양식이 프로젝트마다 달라 모든 양식을 파싱하지는 못합니다.
- **인터락 시뮬레이션 화면은 현재 P-5101A 계열 한 세트만 구현되어 있습니다.** 공정 그래픽은 실제 프로젝트의 화면승인자료를 배치 원천으로 삼기 때문에 태그마다 별도 작화가 필요합니다. 조회·조건 판정은 전 태그에서 동작하며, 그래픽 시뮬레이션만 시연 대상 태그로 한정했습니다.
- 문서 범위를 완전히 벗어난 질의 일부는 검색 점수만으로 판별되지 않습니다. 평가셋에 맞춘 튜닝을 피하기 위해 **고치지 않고 한계로 남겼습니다.**

## 9. 향후 확장

### 9-1. 앱 안에서 자료 교체와 색인 재구축

현재는 데이터 폴더를 환경변수로 지정하고, 자료가 바뀌면 명령줄에서 색인을 다시 만든 뒤 재기동해야 합니다. 실제 운영에서는 계기 교체가 상시로 일어나므로 이 과정이 화면 안에 들어와야 합니다.

**업로드** — Instrument List · IO List · TB List · Interlock List · 도면 · 매뉴얼을 앱에서 올립니다.

**변경 감지** — 엑셀 계열(리스트·인터락)은 파싱만 다시 하면 되므로 즉시 반영됩니다. 재계산이 필요한 것은 **매뉴얼 PDF뿐**입니다. 어떤 자료가 무엇을 필요로 하는지 화면에서 구분해 보여줍니다.

**색인 재구축 버튼과 진행률 표시** — 매뉴얼이 추가·교체되면 버튼 하나로 색인을 다시 만들고, 청킹 → 임베딩 → 저장 단계의 진행률을 프로그레스바로 표시합니다. 수백 청크 단위의 작업이라 진행 상황이 보이지 않으면 멈춘 것인지 도는 것인지 알 수 없습니다.

**증분 처리** — 현재 구조는 청크 id 목록이 하나라도 달라지면 전체를 다시 임베딩합니다. 매뉴얼 한 권을 추가해도 기존 청크 전부가 재계산됩니다. id 단위로 벡터를 보관하고 없는 것만 계산해 합치는 방식으로 바꾸면, 교체된 문서 분량만큼만 비용이 듭니다.

*현 프로토타입은 임베딩 캐시가 다른 모델로 만들어졌거나 색인 내용이 바뀐 경우를 감지해 재구축하도록만 되어 있습니다. 조용히 낡은 벡터를 재사용하면 오류 없이 검색 품질만 무너지기 때문에, 안전한 쪽(전체 재구축)을 택한 상태입니다.*

### 9-2. Siemens 진단 버퍼 직접 연계

현재는 사람이 진단 내용을 보고 질의합니다. 이걸 자동화할 수 있습니다.

S7-400H/410H의 진단 버퍼는 SZL(System Status List) 영역에 있고, `snap7` 라이브러리의 `read_szl(0x00A0)`으로 읽을 수 있습니다. 읽기 전용이라 PLC 운전에 영향을 주지 않습니다.

**1단계** — 진단 버퍼 텍스트 export를 붙여넣으면 파싱해서 이력·매뉴얼과 대조
**2단계** — snap7으로 주기 폴링하여 알람 발생 시점에 자동으로 조회 결과를 띄움

*본 프로토타입에서는 심사 환경에서 재현이 불가능하므로 구현 범위에서 제외했습니다.*
