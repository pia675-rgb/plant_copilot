호출해 보니 벡터가 정상적으로 돌아왔다 — 크레딧 문제가 아니었다.

배치를 키우면 요청 수가 줄어 통과할 것으로 보고 256 으로 올렸으나
더 빨리 죽었다. 반대로 16 으로 줄이니 통과했다. 요청 수가 아니라
분당 토큰 수 제한이었다. 이후 실제 결제로 등급이 올라가면서
재시도 횟수가 크게 줄었다.

**문제 2 — 임베딩을 바꾸면 핵심 기능이 무너진다**

같은 색인(1,210 청크), 같은 평가셋(45 문항), 리랭커 off 조건에서
임베딩 제공자만 바꿔 측정했다.

| 임베딩 | 전체 | code | syn (한글→영문) | en (영문→영문) | body | typo |
|---|---|---|---|---|---|---|
| ollama/bge-m3 | 28/45 | 4/4 | 8/14 | 4/5 | 5/9 | 1/4 |
| openai/3-large | 21/45 | 4/4 | 3/14 | 4/5 | 1/9 | 1/4 |
| openai/3-small | 18/45 | 4/4 | 1/14 | 4/5 | 1/9 | 0/4 |

en(영문 질의)은 세 구성이 모두 4/5 로 같은데, syn(한글 질의로 영문
매뉴얼을 찾는 유형)만 8 → 3 → 1 로 무너진다. 원인이 한글→영문
구간에 있다는 것이 분리되어 드러난다.

모델 크기 문제가 아니다. bge-m3 는 다국어 교차언어 검색을 목표로
만들어진 모델이고, OpenAI 임베딩은 영어 중심 범용 검색에 맞춰져
있다. 훈련 목표가 다르다.

`과잉거절 없음` 이 39/39 → 20/39 로 떨어진 것도 같은 원인이다.
못 찾으니 근거가 부족하다고 판단해 거절해 버린다. 겉으로는
`거절` 점수가 3/6 → 6/6 으로 올라 좋아 보이지만 실제로는
검색 실패의 부작용이다.

**결정**

배포판에서 bge-m3 를 포기할 수 없다. 포기하면 기획서가 내세우는
핵심 기능이 사라진다. 배포 방식을 다시 정해야 한다.

- 컨테이너에서 bge-m3 를 직접 실행 (메모리 2GB 이상, 호스팅 비용 상승)
- bge-m3 급 다국어 임베딩을 제공하는 API 탐색
- 질의 임베딩만 대체 — 현실적이지 않음

**얻은 것**

"다국어 임베딩이 이 프로젝트의 핵심" 이라는 주장을 숫자로 증명하는

### 3. Railway 배포 — 빌드 실패 네 번

배포 자체보다 빌드를 통과시키는 데 시간이 더 걸렸다. 실패할 때마다
오류가 달라졌고, 한 칸씩 앞으로 나아갔다.

| 순서 | 실패 지점 | 원인 | 조치 |
|---|---|---|---|
| 1 | `COPY package-lock.json` | lock 파일이 `.gitignore` 에 걸려 저장소에 없음 | `git add -f` 로 추가 |
| 2 | `RUN npm ci` | 빌드 환경에서 프로세스가 죽음 | node 빌드 단계 자체를 제거 |
| 3 | `COPY ui/react/dist` | `.dockerignore` 가 dist 를 막고 있음 | 해당 줄 삭제 |
| 4 | `COPY utils/` | `utils/` 가 빈 폴더라 git 이 추적하지 않음 | Dockerfile 에서 해당 줄 삭제 |

2 번에서 방향을 바꿨다. 컨테이너 안에서 프론트를 빌드하는 대신
`npm run build` 결과를 저장소에 포함하기로 했다. 실패 지점이
통째로 사라지고 빌드가 가벼워졌다.

대가는 재현 가능성이다. 소스에서 빌드하지 않으므로 README 에
"UI 는 빌드 결과를 저장소에 포함했으며, 재빌드는 `ui/react` 에서
`npm run build`" 라고 명시한다.

4 번은 내 실수였다. Dockerfile 의 COPY 목록을 폴더 목록만 보고
만들었고, 저장소에 실제로 추적되는 파일이 있는지는 확인하지
않았다. 뒤늦게 `git ls-files` 로 대조해 한 번에 정리했다.

**배운 것.** 요약 화면의 마지막 줄만 보고 원인을 짚으려 했던 것이
시간을 가장 많이 잡아먹었다. 3 번 오류는 로그 첫 부분에
`CopyIgnoredFile ... excluded by .dockerignore (line 66)` 이라고
명시되어 있었는데, 전체 로그를 늦게 봤다.

### 4. 포트

빌드가 통과한 뒤에도 화면이 안 떴다. Railway 는 8080 으로
라우팅하는데 Dockerfile 에는 8000 이 박혀 있었다. 환경변수

**확인**

무너지는 경우도 실패로 처리한다 — 문항이 서로 엉켜 있으면 어느 규칙이
깨졌는지 못 가린다.

**검사가 실제로 검출하는지 확인**

통과만 보면 검사가 허수일 수 있어, 지키려는 것을 일부러 망가뜨려 봤다.

### 2. `device_guard` 문항이 0 개였다

평가셋을 돌려 보니 유형별 내역이 이랬다.

```
l1_hit 29 · l3_cross 22 · grade 29 · no_leak 10 · no_search 8 · sort_rule 1
```

스펙 §4-1 의 일곱 유형 중 `device_guard` 만 한 건도 생성되지 않았다.
부정 문항 두 개 중 하나가 통째로 비어 있었던 것이다.

**원인은 생성 조건이 아니라 자료였다.**

| 쌍 | 최대 유사도 | 임계(0.35) 이상 |
|---|---|---|
| 같은 기종 · 다른 태그 | 1.000 | 22 건 |
| 다른 기종 · 다른 태그 | 0.125 | 0 건 |

기종이 다르면 증상 문구도 아예 다르게 적혀 있다. 그래서 `device` 조건을
코드에서 통째로 지워도 전체 세트 문항은 한 개도 안 무너진다. **규칙을
안 재고 있는 상태였다.**

`sort_rule` 에서 이미 같은 판단을 하고 합성 픽스처를 붙여 두었으므로
같은 방식으로 처리했다. 자료에 상황이 없다는 것이 규칙을 안 재도 된다는
뜻은 아니다.

`dg_synth` 는 같은 증상 문구를 기종만 달리해 둘 놓고 **수집과 배제를 한
문항에서 함께** 본다. 배제만 재면 L3 를 지워도 만점이고, 수집만 재면
device 조건을 지워도 만점이라 한쪽만으로는 규칙을 가둘 수 없다.

**변이 시험 (99 → 100 문항)**

| 변이 | 합계 | 무너진 유형 |
|---|---|---|
| 기준 | 100/100 | — |
| L3 매칭 제거 | 73/100 | `l3_cross` 0/22 · `device_guard` 0/1 · `grade` 25/29 |
| 불일치 우선 정렬 제거 | 99/100 | `sort_rule` 0/1 |
| device 조건 제거 | 89/100 | `device_guard` 0/1 · `no_leak` 0/10 |
| 증상 유사도 무시 | 16/100 | 대부분 붕괴 |

스펙에 적어 둔 기대는 "해당 유형만 무너지고 나머지는 유지" 였는데
실제로는 곁가지가 함께 무너졌다. 결함이 아니라 실제 결합이다 — `L3` 를
지우면 `device_guard` 의 수집 쪽 절반이 같이 사라지고, `grade` 는 L3 로만
이력이 잡히던 태그가 카드를 통째로 잃는다. 결합을 감추려고 문항을
쪼개면 규칙을 못 가둔다고 판단해, 스펙 §4-2 표를 실측에 맞게 고쳤다.

정렬 변이만은 한 유형에서 끝났다. 정렬은 수집 범위를 바꾸지 않으므로
그래야 맞다.

### 4. 4D 리포트가 화면과 다른 문서를 내고 있었다

리포트 PDF 를 열어 보니 두 곳이 어긋나 있었다.

**D2 「즉시 조치」가 조치가 아니었다.**

```
[v] 1. Standards Required for Single-Point Calibration
[v] 2. Standards Required for Multi-Point Calibration
```

`server.py` 가 검색 상위 다섯 건의 **청크 제목**을 조치 단계로 쓰고
있었다. 영문 목차 제목에 체크박스를 붙여 "즉시 조치" 로 내보내는
문서였다. 화면에서 LLM 이 만든 `1. 산 라인 에어락 확인 및 배기` 는 PDF 에
들어가지 않았다.

**D3 「현장 이력」이 이력 카드가 아니었다.** 태그로만 거른 목록의 앞
2 건을 그대로 실었다. 3 단 매칭도 불일치 우선 정렬도 안 거치므로,
화면은 불일치 건을 맨 위에 올려 놓고 PDF 는 날짜순 아무 건이나 싣는
상태였다. 같은 조회인데 두 산출물이 다른 근거를 말하면 어느 쪽도 못
믿는다.

**조치**

`ReportRequest` 에 `steps` 를 추가하고 화면이 이미 만든 조치 순서를 그대로
넘기도록 했다. 서버에서 LLM 을 다시 부르지 않는다 — 리포트는 버튼을
누른 자리에서 바로 나와야 한다. 조치 순서를 만들지 않고 바로 PDF 를
누르는 경로는 규칙으로 만든다(불일치 이력을 첫 항목, 매뉴얼은
`매뉴얼 근거 확인:` 으로 이름을 바로잡음).

D3 이력은 `history_index.match` 를 화면과 같은 인자로 불러 채운다.
매칭 근거는 기존 줄 끝에 붙였다 — 4D 양식은 한 장에 들어가야 하고,
레이아웃이 넘치면 조용히 잘리는 구조라 줄을 늘릴 수 없었다.

```
• 현장 이력: 산 잔량 정상 — 산 라인 에어락으로 소모량 오산정 → 산 라인 배기 후 잔량 재산정
    WO-2026-004 · 불일치 · L1 · 소요 60분
```

이력에 다른 태그가 섞일 수 있게 되었으므로 D1 문구도
`동일 태그 과거 이력` → `관련 현장 이력` 으로 고쳤다.

**확인** — `AIT-4002`(정상), `PIT-1010`(abstain, 이력 2 건),

### 5. 같은 근거가 다섯 번 나왔다

`loop error` 로 조회했더니 근거 5 칸이 같은 문장으로 채워졌다.

```
System Error — The instrument has encountered a system error.
Please follow the shutdown procedure and power cycle...   (0.024)
```

**데이터 오류가 아니라 매뉴얼이 그렇다.** M9e 매뉴얼 p.403 이 코드
4000~4400 서른여섯 개에 같은 설명 한 줄을 붙여 놓았다. 추출기는 이미
알아채고 `shared_description: true` 를 남겨 두었는데(37 건 중 34 건),
**검색이 그것을 안 보고 서른여섯 건을 각각 후보로 다뤘다.** 어휘도
벡터도 본문이 같으니 점수가 같고, 결과가 같은 문장으로 채워진다.
근거가 다섯 건인 줄 알았는데 실제로는 한 건이었다.

**조치** — `retrieval/pipeline.py` 에 `_fold_shared` 를 추가했다.
본문이 글자 그대로 같은 코드 묶음은 한 자리만 쓴다.

```
접기 전: Modbus Map / System Error / System Error / System Error / System Error
접기 후: Modbus Map / System Error (코드 4000~4400 · 36종 공통 설명) / System Error / Modbus Map / Modbus Map
```

**접되 숨기지 않는다.** 서른여섯 개 중 하나만 보여주면서 그 사실을
말하지 않으면 근거가 하나뿐인 것처럼 읽힌다. 제목에 범위와 개수를
적고 `trace.folded_codes` 에 코드 목록을 남겼다.

코드 완전일치(`exact_code`)는 접지 않는다. 사용자가 `4001` 을 직접 쳤는데
`4000` 으로 바꿔 보여주면 조회가 아니라 추측이 된다.

**회귀 확인** — `eval_set_v2` 45 문항을 접기 켠 상태와 끈 상태로 각각
채점했고 스코어카드가 바이트 단위로 동일했다. 인터락 67/67,
판넬 211/211, 이력 100/100 도 그대로다.

### 6. 배포 — Dockerfile 의 죽은 단계

`App.jsx` 를 고쳤는데 배포 화면에 반영되지 않아 Dockerfile 을 다시 읽었다.

```dockerfile
FROM node:20-slim AS ui
RUN npm run build                        # 여기서 빌드한 것이

COPY ui/react/dist/ ./ui/react/dist/     # 여기선 안 쓰인다
```

`--from=ui` 가 없으므로 빌드 컨텍스트(= 저장소에 커밋된 `dist/`)에서
복사한다. 1 단계는 시간만 쓰고 버려진다. 8/23 에 "node 빌드 단계 자체를
제거" 하기로 했는데 단계가 남아 있었다.

지금은 커밋된 `dist/` 를 쓰는 방식이 의도이므로 **시연 전에는 손대지
않는다** — 빌드 경로를 바꾸면 배포가 새로 깨질 여지가 생긴다.
대신 `App.jsx` 를 고칠 때마다 `npm run build` 후 `dist/` 를 커밋해야
한다는 것을 절차로 못박았다. 마감 후 `COPY --from=ui` 로 정리한다.

**저장소 비공개 전환** — 제출 안내의 "외부 저장소는 반드시 비공개" 규정에
따라 Private 으로 바꿨다. Railway 는 이미 연결된 저장소라 배포는 유지됐다.

**API 비용** — 운영측 지원 문의는 하지 않기로 했다(8/22 「남은 것」 철회).
개인 부담으로 간다. 8/23 에 DeepInfra 로 옮기면서 임베딩이 100 만 토큰당
0.01 달러 수준이 되었고 호스팅도 월 5~7 달러 선이라, 문의에 드는 시간이
금액보다 크다. 다만 공개 URL 이므로 사용량 상한은 걸어 둔다.

### 7. 리랭커 측정이 틀렸다 — 8/22 결론 철회

기획서 §7 에 넣을 수치를 확정하려고 데모 구성으로 45 문항 4 구성을
다시 돌렸다.

| 구성 | 전체 | code | syn | en | body | typo | wrongdev | abstain |
|---|---|---|---|---|---|---|---|---|
| lexical | 16/45 | 4/4 | 0/14 | 4/5 | 0/9 | 0/4 | 2/3 | 6/6 |
| hybrid | 28/45 | 4/4 | 8/14 | 4/5 | 5/9 | 1/4 | 3/3 | 3/6 |
| **full** | **31/45** | 4/4 | **9/14** | **5/5** | 5/9 | **2/4** | 3/3 | 3/6 |

`full` 이 `hybrid` 보다 3 점 높다. 8/22 에 "리랭커는 점수에 기여하지
않았다 · 전체는 물론 유형별 수치까지 한 칸도 다르지 않았다" 고 기록하고
그 근거로 배포판에서 리랭커를 제거했는데, **그 측정이 틀렸다.**

**원인**

```python
if self.mode == "full" and self.rerank_active and hits:
```

리랭커는 `full` 모드에서만 돈다. `hybrid` 에서는 `COPILOT_RERANK` 를
켜든 끄든 코드가 이 분기에 들어가지 않는다. 즉 그날 비교한 두 값은
리랭커가 적용된 적이 없는 구성끼리의 비교였다.

**무엇을 놓쳤나**

그날도 "설정이 실제로 갈렸는지 의심스러워 두 스코어카드의 실험 조건
줄을 대조했다" 고 적었다. 의심은 맞았는데 확인 대상이 틀렸다. 조건 줄에
찍히는 `rerank=BAAI/bge-reranker-v2-m3` 와 `rerank=off` 는 **설정값이
갈렸다는 뜻이지 적용되었다는 뜻이 아니다.** 봐야 했던 것은 어느 모드에서
잰 값인가였다.

설정을 바꿨는데 점수가 한 칸도 안 움직이면 "효과가 없다" 가 아니라
"설정이 안 읽히고 있다" 를 먼저 의심해야 한다. 이 프로젝트에서 같은
유형으로 세 번 깨졌고(임베딩 캐시 신원 · 챗봇 제공자 인식 · 강등 가시성)
그래서 `selfcheck` 를 만들었는데, 정작 측정 자체에는 같은 장치를 두지
않았다.

**결정 — 배포판은 그대로 둔다**

3 점(6.7%p)을 얻자고 이미지에 torch 약 2GB 가 들어오고, 호스팅 요건이
512MB 급에서 다시 올라간다. 8/23 에 DeepInfra 로 옮기며 얻은 것을
되돌리는 셈이다.

**바꾸는 것은 결정이 아니라 서술이다.** "기여가 0 이라 뺐다" 가 아니라
"3 점을 주지만 배포 비용 대비 효율이 낮아 뺐다" 로 적는다. 전자는
사실이 아니고, 후자는 트레이드오프를 재고 고른 것이다.

배포는 `COPILOT_UI_MODE=hybrid` 고정이므로 공개 URL 의 검색 성능은
28/45 수준이다. 기획서·검증 문서에 대표 수치로 무엇을 싣는지 명시한다 —
`full 31/45(로컬, 리랭커 포함)` 와 `hybrid 28/45(배포 구성)` 를 둘 다
적고 어느 것이 배포 값인지 밝힌다.

**재발 방지**

- 설정 변경 전후 점수가 완전히 동일하면 통과가 아니라 **경고**로 본다.
  변이 시험에서 쓰는 판단(변이를 넣었는데 점수가 그대로면 문항이
  아무것도 시험하지 못한 것)을 측정에도 그대로 적용한다.
- 스코어카드 조건 줄에 설정값만 찍지 말고 **실제 적용 여부**를 함께
  찍는다. `rerank=... (applied in: full)` 형태.

**부수 확인** — `v1` 열은 `demo/sources/error_codes.json` 이 없어
건너뛰었다. v1 은 코드표 306 건만 색인하는 구성이라 그 파일이 필수다.
`demo_derived/error_codes.json` 을 복사하면 채워진다. 기획서 §5 의
AS-IS/TO-BE 비교를 숫자로 뒷받침하는 열이라 채워 둔다.

**또 하나 — `run_eval.bat` 이 전체 세트 자료를 본다.** 데이터 경로 세 줄이
없어서 `data/` · `index/` 를 본다. 오늘 평가가 처음에 엉망으로 나온 것도
이 때문이었다. `run_check.bat` 도 같다. 8/23 에 "환경변수가 세션마다
풀려서 같은 실수를 네 번 반복했다" 고 적고 `env_local.sh` 를 만들었는데,
`.bat` 두 개는 고치지 않은 채로 두었다.

### 1. 인터락 입력 기준 조회가 껍데기였다

화면에서 「입력 태그 기준 조회」를 체크하면 동작 셀렉트만 비활성화되고
**태그 목록은 출력 태그 그대로였다.** `LCV-01 · 출력`이 남은 채로 입력
기준 조회를 하니 빈 결과가 나왔다. 필터가 탭만 보고 걸렀기 때문이다.

**종류(계기/출력)로 거르면 안 되는 조회다.** 인터락 조건에 등장하는
태그를 세어 보니 34건 중 계기 19 · **출력 11** · 어느 목록에도 없는 것
4(AIT-6004, FIT-5006, LIT-7003, TIT-5005)였다. 펌프가 도는 상태가 밸브
개방의 조건이 되는 식으로 출력 장비가 입력 조건에 들어온다. 계기만
남기면 "펌프를 세우면 뭐가 영향받나"를 못 묻는다.

그래서 서버가 실제 조건을 훑어 `in_interlock` 표시를 내려주고 화면이
그것으로 거르게 했다. 인터락에만 등장하는 4건은 목록에 새 항목으로
추가했다 — 빼면 화면에서 조회할 방법이 없는 조건이 생긴다.

입력 기준일 때는 `· 출력` 라벨을 뗐다. 출력이 섞여 있는 것이 정상인데
라벨이 붙어 있으면 잘못 걸러진 것처럼 읽힌다. 계기 리스트에 없는
태그는 제조사·모델 칸이 비므로 `· ` 만 남던 것도 정리했다.

`useEffect` 의존성에 체크박스 상태를 넣는 것을 빼먹으면 목록이 즉시
안 바뀐다 — 이번 버그의 절반이 그것이었다.

### 5. 거절 시 모델 추측 — 격리가 기능의 전부다

근거를 못 찾으면 화면이 통째로 비고, 현장에서는 그 순간 도구를 닫는다.
그래서 abstain 일 때 모델 추측을 붙이기로 했다. **다만 이 기능의
값어치는 추측의 품질이 아니라 격리에 있다.** 근거 있는 답과 추측이
같은 무게로 보이는 순간 "근거 없이 답하지 않는다" 는 전제가 무너진다.

격리 장치 네 겹:
- abstain 판정에서만 생성, advise 에는 절대 미부착
- 조치 배열(steps)에 넣지 않고 별도 필드 — 4D 리포트가 못 읽는다
- 화면은 기본 접힘 + 「매뉴얼 근거 없음 · 모델 추측」 라벨 + 경고문
- 출력에 문서명·페이지·"매뉴얼에 따르면"·근거 번호가 섞이면 통째 폐기

selfcheck 에 「추측 격리 [주입]」을 추가했다(41번째). advise 미부착 ·
steps 분리 · 리포트 미포함 세 가지를 재고, 일부러 steps 에 섞어 넣으면
검출하는 것까지 확인했다.

**침묵 실패를 한 번 저질렀다.** 처음 구현이 `except: return None` 으로
조용히 넘어가서, 화면에 아무것도 안 뜨는데 원인을 알 수 없었다. 이
프로젝트는 검색 강등도 사유를 화면에 남기는데 새 기능만 그 방침을 안
따랐다. `(결과, 사유)` 를 돌려주고 안 나온 이유를 화면에 찍게 고쳤다.
품질은 검증할 방법이 없으므로(정답 없는 출력) 수치를 주장하지 않는다 —
검증 가능한 것은 규칙으로, 불가능한 것은 격리된 참고로.

### 1. 근거 수준 선택 모드 — 근거 / 자유

어제 만든 모델 추측은 거절에서만 나왔다. "확실하지 않아도 보고 싶다"
는 요구가 있었는데, 근거 있는 답 옆에 그냥 붙이면 둘이 같은 무게로
보인다. **모드로 갈랐다** — 사용자가 명시적으로 고른 상태라면 무엇을
보고 있는지 안다. 자유 모드를 켜면 근거를 찾은 조회에도 추측이 붙고,
도우미가 문서 밖 질문에 일반 지식으로 답한다.

모드와 무관하게 지키는 선: 추측은 라벨 붙은 접힌 패널로만, 조치
순서와 4D 리포트에는 어느 모드에서도 안 들어간다(조치로 저장되면
다음 조회의 이력 근거가 되고, 리포트는 결재를 탄다). selfcheck
「추측 격리」에 자유 모드 검사를 더했다. 모드는 새로고침하면 기본으로
돌아간다 — 어느 모드인지 모른 채 화면을 보는 상황이 가장 위험하다.

추측·자유 답변은 **검색 결과를 참조하지 않는다.** abstain 은 못 찾은
상태가 아니라 충분성 미달인 상태라, 그 약한 근거를 프롬프트에 넣으면
인용 검증 없는 경로에서 문장으로 세탁된다. 근거를 아예 안 봐야
「문서 근거 아님」 라벨이 사실이 된다.

챗봇에서 두 번 고쳤다. 처음엔 근거 QA 가 실패해도 그 실패 답변을
그대로 반환해 자유 경로에 못 갔고, 고친 뒤에도 조회 명령으로 해석된
질문은 다른 경로(조회 후속)로 새서 같은 실패를 반복했다. **넘기는
대신 덧붙이는 방식**으로 바꿨다 — 근거 없음을 지우지 않고 그 뒤에
라벨 붙은 모델 답변을 잇는다. 자유 모드를 켠 뜻은 "근거 없어도 참고를
달라" 이지 "근거 없음을 감춰 달라" 가 아니다.

### 2. 배치 경로 고정 — 세 번 반복한 사고를 이제야 막았다

기존 배치가 경로를 설정하지 않고 기본값에 기대고 있었다. 데모 변수가
살아 있는 창에서 실행하면 그것을 물려받는데 화면에는 전체 세트 경로가
찍혔다 — 표시가 사실과 달랐고, 어제 색인 덮임 사고가 이 구조에서
났다. 배치 4종으로 정리: 전체 세트용 둘은 경로 명시, 제출 수치 측정용
(run_eval_demo)과 색인 재구축용(run_rebuild_demo) 신설. 재구축 배치는
경로를 찍고 **pause 로 멈춰** 사람이 확인해야 진행된다.

8/23 일지에 "같은 실수를 네 번 반복했다" 고 적고도 배치를 만들지
않았다. **기록하는 것과 고치는 것은 다른 일이다.**

(잔손질 — 챗봇 창 높이 드래그 조절, 아이콘을 이미지에서 도형(SVG)
으로 교체. 창 크기·위치·글자 조절 등 여섯 기능을 만들었다가 전부
되돌렸다 — 마감 전 조작 방식을 여섯 개 바꾸면 시연에서 무엇이
튀어나올지 모른다.)

### 3. 자료 반입 화면 — 본체는 반입 직후 점검이다

결선이 "심사위원이 미션을 주고 현장 적용하는" 방식이라는 정보를 듣고,
기획서 6-3 확장 계획 중 지금 할 수 있는 것을 앞당겼다.

지금까지 찾은 결함 여섯 종이 전부 자료를 넣는 시점에 생겼고, 답이 안
나오는 형태가 아니라 그럴듯한 답이 나오되 틀린 형태였다. 그래서
올리자마자 리포트를 사람 앞에 놓는다 — 문서별 읽기(행 수, IO List 는
표준 24열 대조), 매뉴얼↔기종 연결(안 된 기종은 "알람 조회가 ABSTAIN
이 됩니다" 예고), 문서 사이 태그 맞물림. **판정은 하지 않는다** —
어느 쪽이 맞는지는 데이터 주인이 안다. 점검 로직은 새로 만들지 않고
tag_registry·selfcheck·색인기의 판별 함수를 재사용했다 — 화면과
색인이 다른 기준을 쓰면 점검이 색인과 다른 말을 하게 된다.

정한 것들: 덮어쓰기 전 `.prev` 보존, 삭제는 2단계(`.deleted` 를
거쳐야 영구 삭제) — 되돌릴 수 없는 조작을 화면 한 번에 만들지
않는다. 재생성은 증분이 아니라 **전체** — 증분은 청크와 벡터가 한
줄만 어긋나도 검색이 조용히 틀리고 점수로도 잘 안 잡힌다. **느린
것과 조용히 틀리는 것 중 느린 쪽을 골랐다.** 증분은 검증 설계와 한
세트로 확장 계획에 남긴다. 재생성은 배경에서 진행률(임베딩 N/M)을
보이며 돈다.

### 4. 점검기를 점검하다 — 고장 주입이 기능을 낳았다

리포트가 뜨는 것과 문제를 잡는 것은 다르다. 일부러 깨진 자료를 넣어
시험했다.

**깨진 IO List** — TAG 열 이름을 바꾼 파일. 리포트가 `표준 열 23/24 ·
빠짐: TAG · 인식 못함: TAG NO` 로 짚었고, 같은 상태에서 판넬 조회가
실제로 깨졌다. 점검 경고와 실제 고장이 일치한다.

**기종 없는 매뉴얼** — DI 카드 매뉴얼을 올렸는데 리포트가 조용했다.
연결 지도가 기종 쪽에서만 보고 있었다 — "매뉴얼 없는 기종" 은 잡아도
"기종 없는 매뉴얼" 은 지나갔다. 역방향을 추가하니 원래 있던 ET200SP
AI 매뉴얼까지 미연결로 떴는데, 계기가 아니라 IO 카드 문서라 그게
사실이었다. 그래서 **카드 문서에 제 자리를 만들었다** — IO 유형을
읽어 해당 포인트 수와 잇는다(AI 카드 문서 "AI 포인트 76점에 해당",
시험용 DI 문서 "DI 포인트가 없습니다 — 잘못 올렸을 수 있습니다").
계기 기종에 억지로 붙이면 거짓 연결이고, 미연결로 두면 쓰이는 문서가
잘못 올린 파일처럼 보인다.

시험 중 실수와 발견도 있었다. 영구 삭제를 되살리기로 착각해 IO List
를 정말 지웠다가 직전에 내려받은 사본으로 복구했다 — 확인창 두 번을
거치고도 실수는 나며, 2단계 삭제가 왜 필요한지 설계자가 몸으로
확인했다. 업로드 실패 오류가 화면 아래에 찍혀 놓치기 쉬웠던 것은
버튼 아래로 옮기고, 종류-확장자 불일치는 보내기 전에 막게 했다.

### 5. 파일 관리를 만들다 핸들 누수를 찾았다

Windows 에서 삭제가 PermissionError — 파일을 쥔 것은 엑셀이 아니라
**서버 자신**이었다. 프로젝트 전체에서 `load_workbook` 을 닫는 곳이
한 군데도 없었다. read_only 워크북의 핸들은 리눅스에선 티가 안 나고
Windows 에서는 이름 변경·삭제를 막는다. 읽기만 하던 동안 잠복했다가
파일을 바꾸는 기능을 만들자 드러났다. 여덟 곳을 닫게 고치고 회귀
확인(태그 104 · 인터락 67/67). 개발 환경(리눅스)에서는 재현조차 안
되는 결함 — **실행 환경에서 굴려 본 것이 잡았다.**

색인 재생성 중 도우미를 썼다가 llama3.2 와 bge-m3 가 4GB GPU 를 다퉈
임베딩이 576/1210 에서 죽는 것도 겪었다. 실패 지점·사유가 화면에
남아(설계대로) 다시 돌려 복구, 안내문에 "재생성 중 조치 생성·도우미

문제다.

시험 후 원상 복구: 시험 매뉴얼 삭제 → 재생성 1,210건 → **28/45 ·
2/10 · 67/67, 문항별 정오까지 동일.** run_eval_demo.bat 이 첫
실전에서 제 몫을 했다.

### 3. 알람이 매뉴얼에 없는 말을 한다

4D 리포트의 D3(원인)에 이상한 것이 실려 있었다. "power off"로 검색하니
**전원을 끄는 절차 문서**(p.116 Shutting Down)가 원인 근거로 올라온 것이다.
검색은 정상 동작이었다 — 알람은 장비가 *꺼져 있다는 상태*를 말하고 매뉴얼은
장비를 *끄는 절차*를 말하는데, 문자열이 같으니 구분할 방법이 없다.

어디까지 어긋나 있는지 색인을 전수 검색했다.

```
loop error   0건
high high    0건
low low      0건
```

SCADA가 실제로 보내는 알람명(HH · LL · LOOP ERROR · ON/OFF COMMAND와 카드
SSL 진단 코드)이 **매뉴얼에 하나도 없다.** 매뉴얼은 벤더가 쓰고 알람명은
SCADA 엔지니어가 쓴다. 접점이 없는 것이 정상이다.

이 과정에서 입력이 원래 **두 단계**라는 것도 정리됐다. 1단계는 원격(SCADA
알람명 + SSL 코드), 2단계는 현장(계기 화면 코드 + 눈으로 본 증상)이다.
화면의 "계기 화면 코드" 칸은 원래 정확했고, SSL은 그 칸이 아니라 알람 쪽에
붙어야 할 것이었다.

### 4. 고친 것

**SSL 코드 조회** — `11H`, `8H` 같은 16진 코드가 아예 조회되지 않았다.
완전일치 정규식이 십진 숫자만 잡고 있었다. 패턴을 넓혀 카드 진단 코드
24종이 전부 조회된다. 넓히자 태그 `AIT-4002`의 숫자부 `4002`가 코드로
오인되는 것이 딸려 나와, 태그를 먼저 걷어낸 뒤 코드를 뽑도록 했다.

**알람 라우팅** — 알람 5종을 식별해 매뉴얼·코드표의 실제 어휘로 확장한다.
확장어의 출처는 평가셋이 아니라 카드 진단표와 트러블슈팅 장의 표제어다.
확장할 때 **알람명 자체는 검색어에서 뺐다** — M9e에서 "loop"는 수처리
배관(DI Loop)을 뜻하는 가짜 친구여서, 남겨 두면 엉뚱한 절이 올라온다.

채점에도 손을 댔다. 예전에는 확장 검색으로 정답을 찾아 놓고 채점은 원문
"LOOP ERROR"로 적중률을 재서 거절해 버렸다. **정답을 찾고도 버리는**
구조였다.

**알람 폭주 역추적** — AIT-4002는 카드 하나(RIO-01/DP11/R0/S8)를 네 태그와
함께 쓴다. 카드가 죽으면 다섯 점이 동시에 LOOP ERROR를 내고, 그때 개별 태그
조회는 다섯 번 다 오답이다. 진짜 원인은 카드 한 장이다. 동시 알람 태그의
공통 조상을 카드→랙→판넬→PLC→흩어짐 4계층으로 판정하는 조회를 넣었다.
같은 카드인데 **알람이 안 뜬 동반 태그**는 반례로, 색인에 없는 태그는
미등재로 분리한다 — 모른다와 반례는 다른 것이다.

**4D 정직성** — 매뉴얼 근거가 없는 조회에서 D3가 조용히 비는 대신 "매뉴얼
근거: 없음 — 이력 기준으로 판단"을 명시한다. 없으면 없다고 쓴다.

**데모 IO List 채널 중복 7건** — 같은 카드 같은 채널에 두 태그가 앉아 있었다.
실물이라면 배선이 불가능한 자료다. 재배정하며 스크립트 1차본에 `str(v or '')`
가 **CH=0을 빈 값으로 삼키는** 버그가 있었다. 0이 유효값인 칸에서 falsy 검사를
하면 안 된다는 것을 다시 배웠다.

이 넷을 지키는 자기 점검 가드도 함께 넣었다. 그중 하나는 **평가 448문항에서
알람 라우팅이 발화하면 실패**한다 — 새 규칙이 평가 점수를 몰래 움직이는 일을
상시 감시하는 장치다.

### 5. 오늘 틀린 것, 그리고 우리가 낸 사고 하나 더

**하나, 진단을 두 번 틀렸다.** "기기 필터가 카드 코드를 막는다"고 했는데
코드를 열어 보니 필터는 카드를 항상 통과시키고 있었다. 실제 결함은 정규식
하나뿐이었다. 또 `COPILOT_DIVERSIFY`를 켜자고 했는데, 이미 측정으로 기각된
설정이었다(off 33 > kind 29 > all 27). 저장소에 그것을 지키는 가드까지
있었다. 둘 다 철회하고 패치 노트에 정정으로 남겼다.

**둘, 자신 있게 어긋난 답.** 고친 것을 화면에서 시험하는데 `loop error`를
소문자로 쳤더니 라우팅이 발화하지 않았다. 판별을 대문자 원문으로만 하고
있었던 것이다. 화면에는 충분성 **1.00**으로 "System Error — power cycle
하라"는 범용 문구와 DI loop(배관) 절이 실렸다. 거절보다 나쁜 상태다 —
틀렸는데 확신에 차 있다. SCADA는 대문자로 보내지만 사람은 소문자로 친다.
두 단어짜리 구문은 대소문자를 무시하도록 넓히고, 오인 여지가 있는 축약형
`HH`/`LL`만 대문자를 유지했다. **첫 실사용 입력이 잡아낸 결함이다.**

**셋, 자료 폴더를 잘못 보고 놀랐다.** 자기 점검을 돌리니 16건이 실패했다.
집 PC에는 실물 자료(`data/`)가 없는데 실물 전용 배치를 돌려, 로더가 다른
자료(76점)로 흘러간 것이었다. 채널 중복 가드가 실패로 뜬 것도 내가 고친
자료가 아니라 그 자료의 중복을 정직하게 잡아낸 결과였다. 데모 배치로 다시
돌리니 전부 정상. 배치 파일이 경로를 못 박아 둔 이유(8/26)를 오늘 다시
확인한 셈이다.


**넷, 홀드아웃 한국어판이 영문판으로 덮여 있었다 — 네 번째 덮임 사고.**
외부 코드 검토(다른 AI 두 종에 저장소를 주고 받은 검토)가 잡아냈다.
`eval_set_holdout.json`(한국어판)과 `_en.json`(영문 대조군)이 **완전히 같은
영문 파일**이었다. 영문판을 만들 때 원본을 고쳐 저장한 것으로 보인다 —
다른 이름으로 저장이 빠진 채 8/25 첫 커밋에 그대로 들어갔다.

측정까지 의심해야 했다. 저장소만 보면 "한국어 2/10"이 실제로는 같은 영문
파일을 두 번 돌린 것일 수도 있었다. 다행히 **8/25 스코어카드가 커밋에 남아
있었다** — 실패 8건의 한국어 문항과 문항별 점수가 그대로였고, 영문판과
프로필이 달랐다(한국어는 H01을 0.49로 거절, 영문은 0.90으로 통과). 두
측정은 진짜 별개였다.

백업에서 한국어 초안 파일을 찾았다. 옛 태그 체계(PW-TOC-01)라 그대로는 못
쓰고, 문항 본문은 초안에서 · 태그와 기대답 배선은 영문판에서 가져와
합쳤다. 합치기 전에 초안의 실패 8건이 스코어카드 기록과 접두까지 일치하는
것을 확인했다. 복원 후 재측정 — **2/10, 통과 문항(H06·H08)까지 8/25와
동일하게 재현됐다.**

세 가지가 이 복구를 가능하게 했다. 문항별 정오를 기록해 둔 것, 스코어카드를
코드와 같이 커밋해 둔 것, 백업. 총점만 적었다면 "한국어 2/10"과 "영문
2/10"이 같은 측정인지 다른 측정인지 영영 구분할 수 없었다 — 실제로 두
측정은 총점이 같고 **통과 문항이 달랐다**(한 H06·H08 / 영 H07·H08).

덮임 사고가 이것으로 네 번째다(색인 3회 + 평가셋 1회). 색인은 배치 파일로
경로를 못 박아 재발을 막았는데, 평가셋 파일에는 그런 장치가 없었다.
내보내는 파일과 원본이 한 폴더에 있는 한 이 사고는 또 난다.

**확인**

데모 세트 재측정 — **45문항 hybrid 28/45 · 홀드아웃 2/10 · 인터락 67/67.**
기준선 그대로, 회귀 0. 유형별로도 동일하다(code 4/4 · wrongdev 3/3 ·

수치가 오르지 않은 것도 설계대로다. 45문항은 자연어 질의 세트라 SCADA 알람
어휘가 등장하지 않고(라우팅 발화 0건), 이번에 고친 것은 평가셋에 없는 **입력
경로**다. 올랐다면 오히려 평가셋 오염을 의심해야 했다.

복원한 한국어 홀드아웃 재측정은 2/10 — 8/25와 통과 문항까지 동일 재현.

알람 경로는 따로 실측해 시연 시나리오 문서에 적었다. `loop error` 조회가
거절에서 **advise 0.93**으로 바뀌고, 근거 다섯 건이 카드 4 + 계기 1로 선다 —
1위 ET200SP `Supply voltage missing`(카드가 본 것), 5위 M9e p.274 `The
Analyzer Will Not Power On`(계기 쪽 원인 후보). 폭주 역추적은 다섯 태그를
넣으면 카드를 지목하고, 넷으로 줄이면 남은 하나를 반례로 짚는다.

### 2. 만든 것 — 사람이 반복하던 두 가지

어디에 에이전트를 넣을지가 아니라 **사람이 여러 단계를 반복하는 곳이
어디인가**로 접근했다. 두 곳이었다.

**반입 수리 보조** — 점검 리포트가 지적을 내면 사용자가 엑셀을 열어 고치고
다시 올린다. 그 왕복을 줄인다. 다만 **제안과 반영을 갈랐다.** 자동으로
고치는 것은 정답이 계산되는 두 종류(채널 중복 재배정, 헤더 오기 복원)뿐이고,
태그 오타처럼 의미가 걸린 것은 후보만 보이고 사람이 판단한다. 반영은 승인한
것만, 열쇠를 가진 요청만. 반영 전 `.prev` 보존, 반영 후 재점검 수치를 보인다
— 고쳤다고 말하는 대신 점검을 다시 통과하는지로 보인다.

`apply` 는 화면이 보낸 내용을 믿지 않는다. 서버가 제안을 새로 계산해 id 가
맞는 것만 반영한다. 화면을 띄워 둔 사이에 파일이 바뀌었으면 그 제안은
무효가 된다.

**동시 알람 조사** — 카드 한 장이 죽으면 물린 계기 전체가 운다. 그때의 조사
절차는 정해져 있다(공통 조상 → 반례 → 코드 근거 → 종합). 여섯 단계를 대신
밟고 **밟은 단계를 전부 남긴다.** 결론은 규칙으로 조립하며 LLM 을 쓰지
않는다 — 같은 입력에 같은 보고가 나와야 한다.

자율성의 경계를 분명히 뒀다. 이 조사기가 정하는 것은 **어느 조회를 다음에
부를지**뿐이고, 각 조회의 답은 이미 전건 검증된 계층(판넬 색인 211/211,
코드 완전일치)이 보장한다. 정답이 하나인 조회에는 에이전트를 쓰지 않는다.

### 3. selfcheck 18건 실패 — 반나절을 오진했다

환경변수 없이 `python eval\selfcheck.py` 를 돌렸더니 18건이 실패했다.
채널 중복 7건, 스테이션·랙 겹침 8건, 인터락 62문항 실패… 각기 다른 결함처럼
보였다.

**전부 하나의 원인이었다.** 환경변수가 없으면 기본 경로가 실물 트랙
(`data/`)을 가리키는데, 그 폴더를 프로젝트 밖으로 옮겨 둔 상태였다. 그리고
마이그레이션 잔재인 폴백 한 줄이 v1 원본(76점)으로 조용히 갈아탔다.

가장 나빴던 것은 **경고가 안 떴다는 것**이다. 시작 로그의 가드가 폴백 *후* 의
경로를 검사해서, 없는 폴더를 `[config] DATA_DIR = ...\data` 로 멀쩡하게
찍었다. 이 한 줄 때문에 원인 추적이 반나절 늦어졌다.

데모 트랙으로 다시 돌리니 **51항목 전건 통과.** 코드도 데이터도 정상이었다.

이 함정은 인수인계 문서에 이미 경고로 적혀 있었다. **적어 두는 것만으로는
막히지 않는다는 것이 오늘 증명됐다.** 색인 덮임을 배치 파일로 막은 것과 같은
조치가 점검 쪽에는 없었다 — 구동·평가·색인에는 데모 전용 배치가 있는데
점검만 없어서, selfcheck 은 맨손으로 칠 수밖에 없는 구조였다.

오진하는 동안 세 가지를 "실제 결함"으로 판단했다가 전부 철회했다. 생성기가
채널을 유일하게 배정하지 않는다는 판단(정반대였다 — 생성기가 고쳐 주는데
안 거친 것), 스테이션 겹침이 가정값 문제라는 판단, 그리고 배포본도 같은
증상일 것이라는 판단(Dockerfile 에 데모 경로가 박혀 있어 처음부터 정상).

### 4. 빼기로 한 것 — SSL

SSL 진단 코드가 **계기가 아니라 카드가 내는 신호**라는 것을 다시 짚었다.
지금 화면은 태그를 고르고 시작하는 구조라 축이 맞지 않는다. 코드가 여러 개
몰리면 근거 다섯 건에서 잘리는데 잘렸다는 표시도 없다.

기능은 남기고 **시연과 설명서에서만 뺐다.** 코드 조회 자체는 잘 되고 평가
code 4/4 이므로 없앨 이유가 없다. 대신 기획서 4-5에 "조회 축의 불일치"를
한계로 적고, 해법(카드 단위 조회 화면)을 확장 계획에 남겼다.

알람 폭주도 시연 영상에서 뺐다. SCADA 와 연결돼 있지 않아 "동시에 떴다"는
사실 자체를 도구가 모르고, 사람이 태그를 넣어 줘야 한다. 화면에 보여줄 것이
JSON 뿐이라 장면으로 성립하지 않는다. 대신 장면 1의 동반 태그 설명에 흡수
하고, 연결이 안 돼 있다는 사실을 대사에 넣었다.

**확인**

데모 트랙 재측정 — **45문항 28/45 · 홀드아웃 2/10 · 인터락 67/67 ·
판넬 211/211**, 문항별 정오까지 어제와 동일. selfcheck **51항목 전건 통과**
(신규 가드 3종 포함 — 수리안 왕복, 수리 반영 열쇠, 동시 알람 조사).

### 1. 도구를 하나 더 만들었다

시연 영상 촬영이 생각보다 큰 벽이었다. **화면과 음성을 동시에 녹화하면**
말이 꼬일 때마다 처음부터 다시 찍어야 하고, **나눠서 찍으면** 편집 도구를
새로 배워야 했다. 5분 무편집이라는 조건 때문에 잘라 붙일 수도 없었다.

그래서 그 일만 하는 도구를 만들었다. 네 단계다 — **찍기 → 대본 → 목소리
→ 내보내기.**

- **찍기**: 브라우저 화면 녹화(`getDisplayMedia`). 실제 화면을 그대로 담는다
- **대본**: 장면별 자막 구간(cue)을 시간축에 배치
- **목소리**: 대본을 음성으로 만들어 얹거나 직접 녹음
- **내보내기**: 원본 소리·내레이션 음량을 섞고 자막을 태워 한 파일로

**화면은 AI 가 만들지 않는다.** 실제 조작을 그대로 녹화하고, AI 는 대본
문장과 음성에만 쓴다. 제출 안내가 "실제로 얼마나 걸리는지도 확인하고자
한다"고 못 박고 있어서, 화면을 손대는 순간 제출물의 의미가 없어진다.

5분 상한과 4분 30초 경고선을 코드에 상수로 박았다. 편집하다 넘기는 일을
막으려고 조건을 도구 쪽에 옮겨 놓은 것이다.

### 2. 이게 옳은 선택이었나

마감 나흘 전에 새 도구를 만드는 건 위험한 판단이다. 다만 두 가지가
달랐다.

**본체와 완전히 분리돼 있다.** 저장소가 다르고, `plant_copilot` 의 코드는
한 줄도 건드리지 않는다. 잘못돼도 검증 수치에 영향이 없다.

**대안이 더 비쌌다.** 동시 녹화로 4~5회 재촬영하거나, 편집 도구를 익히는
시간이 도구를 만드는 시간과 비슷했다. 그리고 소개 영상과 시연 영상 두
편을 만들어야 했으므로 두 번 쓸 수 있었다.

### 3. 만들면서 부딪힌 것

영상은 **시간축이 곧 자료 구조**다. 자막 하나가 몇 초에 시작해 몇 초에
끝나는지, 그게 화면의 어느 조작과 맞물리는지를 전부 다뤄야 한다. 정비
도구를 만들 때와는 다른 종류의 문제였다 — 그쪽은 "이 태그의 근거가
무엇인가"였고, 이쪽은 "이 순간에 무엇이 보이고 무엇이 들리는가"다.

내보내기에서 자막을 화면에 태우는 것과 별도 트랙으로 두는 것을 고르게
했다. 태우면 어디서나 보이지만 되돌릴 수 없고, 분리하면 재생기가 지원해야
한다. **되돌릴 수 없는 조작은 기본값으로 두지 않는다**는 본체의 원칙을
여기서도 썼다.

**확인**

소개 영상과 시연 영상 두 편 제작 완료. 시연 영상은 배포 주소를 실제로
조작한 화면이며 배속·컷 편집 없음.

### 2. 화면과 챗봇이 서로 다른 것을 보고 있었다

첫 두 건은 뿌리가 하나다. 챗봇 후속 질문은 "화면에 떠 있는 결과" 를
근거로 답하는데, 그 `context` 가 담는 것이 **알람 조회 근거뿐**이었다.
인터락을 조회하면 화면은 인터락 탭인데 `context` 에는 직전 알람의
매뉴얼 근거가 그대로 남아 있었다. 챗봇은 그것으로 답을 만들었다.

**사용자가 보는 것과 챗봇이 보는 것이 달랐다.** 조용히 틀리는 종류다.

고치면서 인터락을 문장으로 풀어 주는 모듈을 새로 만들었는데,
**LLM 을 쓰지 않았다.** 인터락은 리스트에서 읽은 사실이고 같은 조회에
같은 문장이 나와야 한다. 모델이 다시 쓰면 조건이 슬쩍 바뀔 수 있고, 그
위험은 정비 지시에서 감당할 수 없다. 만들면서 세 군데를 더 고쳤다 —
태그 없는 조건(`MOTOR OVERLOAD TRIP`)을 상태 코드(`FAULT`)로만 줄이면
뜻이 사라지는 것, `AUTO` 를 수동 리셋으로 잘못 말하던 것, 분류 이름.

### 3. 묻는 사람에게 답 대신 행동이 나갔다

세 번째가 특히 나빴다. "판넬 조회로 나는 어떤걸 알 수 있지?" 는 질문인데
**알람 조회가 실행됐다.** 기능 명사가 들어간 문장을 명령으로만 봤기
때문이다. 질문 표지가 있으면 명령·인사 규칙보다 먼저 안내로 답하도록
고치고, 기능별 안내 여덟 가지를 규칙 안에 넣었다.

네 번째는 숨어 있던 기존 결함이다. `by_panel` 의 반환 키가 바뀌었는데
챗봇 응답 조립 한 줄만 옛 이름을 읽고 있었다. 기존 가드는 **라우팅
판정까지만 보고 응답 조립은 보지 않아서** 잡지 못했다. 새 가드는 실제로
호출해 예외가 나는지까지 본다. **점검이 어디까지 보는지가 곧 무엇이
숨을 수 있는지다.**

### 4. 자유 모드가 자유롭지 않았던 이유

다섯 번째는 두 겹이었다. 판넬 조회가 `IW512+` 같은 단자 번호를 화면에
띄워 놓고, 그것을 되물으면 답하지 못했다. **방금 자기가 보여준 값을
모르는 셈이었다.** 자료에는 있었고 규칙만 없었다.

그리고 그때 자유 모드였는데도 모델에게 물어보지조차 않았다. 규칙이 못
잡으면 모델이 답하도록 표식까지 달아 두었는데, 그 앞의 질문 판정에
**"뭐지·뭐야" 가 빠져** 있었다. `뭐가`·`뭔` 은 있고 `뭐` 가 없었다.

사용자는 이것을 "자유도가 너무 낮다" 고 표현했다. 모드 설계 문제로
보이지만 실제로는 정규식 한 조각이었다. **증상의 이름과 원인의 자리는
자주 다르다.**

보였다. 그중 둘은 같은 판넬(CUB-B) 안이었다.

한 PLC 안에서 입력 주소가 겹치는 배선은 성립하지 않는다. 배선을 조회하는
도구가 배선이 불가능한 값을 내놓고 있었다.

원인은 `tools/make_tb_list.py` 의 주소 계산 한 줄이었다.

```
base = "IW%d" % (500 + slot * 10 + ch * 2)
```

슬롯과 채널만 썼다. 스테이션(PN(DP))·랙이 빠져 다른 카드의 같은 자리가
같은 주소를 받았다. 게다가 슬롯 간격 10 에 16채널(폭 32)을 담아 옆 슬롯을
침범했다 — S4/CH6 과 S5/CH1 이 둘 다 52 가 됐다. 디지털 단자블록도 슬롯만

주소 배치를 실제 PLC 처럼 계층으로 다시 잡았다 — 슬롯 64, 랙 2048,
스테이션 16384. **IO List 는 건드리지 않았다.** 태그·판넬·카드·채널
배치는 그대로이고 단자 번호만 다시 붙었다. 단자 번호 종류가 71종에서

판넬 평가셋 6문항이 옛 단자 번호를 기대값으로 갖고 있어 실패로 떴다.
평가셋은 자료에서 자동 생성되므로 다시 만들었다. **점수를 맞추려고 문항을
고친 것이 아니라 자료가 바뀌어 정답이 바뀐 것이다** — 문항 수(211)와 유형
구성은 그대로다. 이 구분이 흐려지면 평가셋 맞춤이 된다.

가드로 `단자 번호 유일성 [주입]` 을 넣었다. 패치 27에서 채널 유일성을
넣을 때 **카드 층만 보고 단자 층은 보지 않았던 것**을 메운다. 같은 성질의
결함이 층을 바꿔 남아 있었던 셈이다.

그리고 아직 "말" 에 남아 있던 자리를 하나 찾았다. 구동·평가·색인에는 데모

### 2. 배치를 만들자 결함 셋이 따라 나왔다

처음 돌린 자리에서 전부 드러났다.

**① 인터락 자료 판정이 폴더를 몰랐다.** `config.INTERLOCK_XLSX` 는 파일일
수도 폴더일 수도 있다 — 실물 인터락 리스트가 여러 엑셀로 나뉘어 오기
때문이다. 그런데 점검은 `isfile` 만 봤다. 자료는 멀쩡한데 "없음" 이라고
보고했고, 같은 자료로 인터락 조회는 67/67 을 냈다. **점검이 틀렸는데 자료를
탓하고 있었다.**

**② 실패를 찍고도 통과시켰다.** preflight 가 `--strict` 일 때만 종료 코드
1 을 냈다. 화면에 "실패 2건" 을 출력하고 그대로 다음 단계로 넘어갔다.
검사가 실패를 보고서 통과시키는 것은 검사가 없는 것보다 나쁘다 — 봤다고
착각하게 만든다.

**③ 그것을 잡으려고 만든 가드가 거짓으로 실패했다.** preflight 메시지에
cp949 에 없는 글자(em dash)가 있어, 콘솔에서는 멀쩡하다가 출력을 파이프로
받는 순간 `UnicodeEncodeError` 로 죽었다. 그 죽음이 종료 코드 1 로 나타나
**가드가 막은 것처럼 보이기까지 했다.** 가드가 예외와 게이트를 구분하지
못하면 거짓 통과를 낸다. 그래서 stderr 의 Traceback 을 따로 보게 했고,
preflight 자체도 출력 인코딩을 utf-8 로 고정했다.

| 6 | 범위 밖 질문이 매뉴얼 검색으로 흘러 무관한 인용이 붙는다 | 라우팅 |

**1번이 리허설의 값어치를 보여준다.** 도남진이 "알람 조회 버튼이
안 눌린다" 고 했다. 고장이 아니라 증상을 적어야 눌리는 것이었는데,
**왜 회색인지 화면이 말해 주지 않는다.** 만든 사람은 아는 것이고 처음
쓰는 사람은 모르는 것이다. 심사위원도 같은 자리에서 멈출 수 있다.

**3번은 성격이 다르다.** 나머지가 불편이라면 이건 **도구가 서로 다른
값을 말하는** 것이다. `TIT-1012` 의 단자를 조회하면 `IW568+` 인데 배치도에는
`TB4-19` 로 적혀 있다. 어제 단자 번호를 PLC 주소 체계로 다시 붙이면서
(패치 30) 도면이 갱신되지 않았다.

검색 45문항도, 판넬 211문항도, 자기 점검 54항목도 이것을 잡지 못했다.
**두 산출물을 나란히 놓고 봐야 보이는 종류**이기 때문이다. 각각은
자기 안에서 일관되다.

여섯 건 모두 결선 과제로 넘겼다. 마감이 다음 날이고 전부 화면·도면·
라우팅 변경이라 재측정이 따른다. 다만 **3번은 오늘 한계로 적었다**
(검증 결과 정리 4-5). 심사위원이 먼저 발견하는 것과 우리가 적어 둔 것을
발견하는 것은 다르다.
