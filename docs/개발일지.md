**추가 · 심야 2 — 클라우드 임베딩 검증**

**문제 1 — 429 가 계속 났다**

`text-embedding-3-large` 로 색인을 만들려니 429 Too Many Requests 로
중단됐다. 처음에는 크레딧 부족으로 판단했다. curl 로 단건을 직접
호출해 보니 벡터가 정상적으로 돌아왔다 — 크레딧 문제가 아니었다.

배치를 키우면 요청 수가 줄어 통과할 것으로 보고 256 으로 올렸으나
더 빨리 죽었다. 반대로 16 으로 줄이니 통과했다. 요청 수가 아니라
분당 토큰 수 제한이었다. 이후 실제 결제로 등급이 올라가면서
재시도 횟수가 크게 줄었다.

**문제 2 — 임베딩을 바꾸면 핵심 기능이 무너진다**

같은 색인(1,210 청크), 같은 평가셋(45 문항), 리랭커 off 조건에서
임베딩 제공자만 바꿔 측정했다.

| 임베딩 | 전체 | code | syn (한글→영문) | en (영문→영문) | body | typo |
|---|---|---|---|---|---|---|
| ollama/bge-m3 | 28/45 | 4/4 | 8/14 | 4/5 | 5/9 | 1/4 |
| openai/3-large | 21/45 | 4/4 | 3/14 | 4/5 | 1/9 | 1/4 |
| openai/3-small | 18/45 | 4/4 | 1/14 | 4/5 | 1/9 | 0/4 |

en(영문 질의)은 세 구성이 모두 4/5 로 같은데, syn(한글 질의로 영문
매뉴얼을 찾는 유형)만 8 → 3 → 1 로 무너진다. 원인이 한글→영문
구간에 있다는 것이 분리되어 드러난다.

모델 크기 문제가 아니다. bge-m3 는 다국어 교차언어 검색을 목표로
만들어진 모델이고, OpenAI 임베딩은 영어 중심 범용 검색에 맞춰져
있다. 훈련 목표가 다르다.

`과잉거절 없음` 이 39/39 → 20/39 로 떨어진 것도 같은 원인이다.
못 찾으니 근거가 부족하다고 판단해 거절해 버린다. 겉으로는
`거절` 점수가 3/6 → 6/6 으로 올라 좋아 보이지만 실제로는
검색 실패의 부작용이다.

**결정**

배포판에서 bge-m3 를 포기할 수 없다. 포기하면 기획서가 내세우는
핵심 기능이 사라진다. 배포 방식을 다시 정해야 한다.

- 컨테이너에서 bge-m3 를 직접 실행 (메모리 2GB 이상, 호스팅 비용 상승)
- bge-m3 급 다국어 임베딩을 제공하는 API 탐색
- 질의 임베딩만 대체 — 현실적이지 않음

**얻은 것**

"다국어 임베딩이 이 프로젝트의 핵심" 이라는 주장을 숫자로 증명하는
자료가 생겼다. 배포 편의를 위해 바꿔 보았더니 핵심 기능이 무너지는
것을 측정으로 확인했고, en 유형이 동일하다는 점이 원인을 한글→영문
구간으로 특정해 준다. 3_검증결과와 1_기획서 양쪽에 넣는다.

### 3. Railway 배포 — 빌드 실패 네 번

배포 자체보다 빌드를 통과시키는 데 시간이 더 걸렸다. 실패할 때마다
오류가 달라졌고, 한 칸씩 앞으로 나아갔다.

| 순서 | 실패 지점 | 원인 | 조치 |
|---|---|---|---|
| 1 | `COPY package-lock.json` | lock 파일이 `.gitignore` 에 걸려 저장소에 없음 | `git add -f` 로 추가 |
| 2 | `RUN npm ci` | 빌드 환경에서 프로세스가 죽음 | node 빌드 단계 자체를 제거 |
| 3 | `COPY ui/react/dist` | `.dockerignore` 가 dist 를 막고 있음 | 해당 줄 삭제 |
| 4 | `COPY utils/` | `utils/` 가 빈 폴더라 git 이 추적하지 않음 | Dockerfile 에서 해당 줄 삭제 |

2 번에서 방향을 바꿨다. 컨테이너 안에서 프론트를 빌드하는 대신
`npm run build` 결과를 저장소에 포함하기로 했다. 실패 지점이
통째로 사라지고 빌드가 가벼워졌다.

대가는 재현 가능성이다. 소스에서 빌드하지 않으므로 README 에
"UI 는 빌드 결과를 저장소에 포함했으며, 재빌드는 `ui/react` 에서
`npm run build`" 라고 명시한다.

4 번은 내 실수였다. Dockerfile 의 COPY 목록을 폴더 목록만 보고
만들었고, 저장소에 실제로 추적되는 파일이 있는지는 확인하지
않았다. 뒤늦게 `git ls-files` 로 대조해 한 번에 정리했다.

**배운 것.** 요약 화면의 마지막 줄만 보고 원인을 짚으려 했던 것이
시간을 가장 많이 잡아먹었다. 3 번 오류는 로그 첫 부분에
`CopyIgnoredFile ... excluded by .dockerignore (line 66)` 이라고
명시되어 있었는데, 전체 로그를 늦게 봤다.

### 2. `device_guard` 문항이 0 개였다

평가셋을 돌려 보니 유형별 내역이 이랬다.

```
l1_hit 29 · l3_cross 22 · grade 29 · no_leak 10 · no_search 8 · sort_rule 1
```

스펙 §4-1 의 일곱 유형 중 `device_guard` 만 한 건도 생성되지 않았다.
부정 문항 두 개 중 하나가 통째로 비어 있었던 것이다.

**원인은 생성 조건이 아니라 자료였다.**

| 쌍 | 최대 유사도 | 임계(0.35) 이상 |
|---|---|---|
| 같은 기종 · 다른 태그 | 1.000 | 22 건 |
| 다른 기종 · 다른 태그 | 0.125 | 0 건 |

기종이 다르면 증상 문구도 아예 다르게 적혀 있다. 그래서 `device` 조건을
코드에서 통째로 지워도 실데이터 문항은 한 개도 안 무너진다. **규칙을
안 재고 있는 상태였다.**

`sort_rule` 에서 이미 같은 판단을 하고 합성 픽스처를 붙여 두었으므로
같은 방식으로 처리했다. 자료에 상황이 없다는 것이 규칙을 안 재도 된다는
뜻은 아니다.

`dg_synth` 는 같은 증상 문구를 기종만 달리해 둘 놓고 **수집과 배제를 한
문항에서 함께** 본다. 배제만 재면 L3 를 지워도 만점이고, 수집만 재면
device 조건을 지워도 만점이라 한쪽만으로는 규칙을 가둘 수 없다.

**변이 시험 (99 → 100 문항)**

| 변이 | 합계 | 무너진 유형 |
|---|---|---|
| 기준 | 100/100 | — |
| L3 매칭 제거 | 73/100 | `l3_cross` 0/22 · `device_guard` 0/1 · `grade` 25/29 |
| 불일치 우선 정렬 제거 | 99/100 | `sort_rule` 0/1 |
| device 조건 제거 | 89/100 | `device_guard` 0/1 · `no_leak` 0/10 |
| 증상 유사도 무시 | 16/100 | 대부분 붕괴 |

스펙에 적어 둔 기대는 "해당 유형만 무너지고 나머지는 유지" 였는데
실제로는 곁가지가 함께 무너졌다. 결함이 아니라 실제 결합이다 — `L3` 를
지우면 `device_guard` 의 수집 쪽 절반이 같이 사라지고, `grade` 는 L3 로만
이력이 잡히던 태그가 카드를 통째로 잃는다. 결합을 감추려고 문항을
쪼개면 규칙을 못 가둔다고 판단해, 스펙 §4-2 표를 실측에 맞게 고쳤다.

정렬 변이만은 한 유형에서 끝났다. 정렬은 수집 범위를 바꾸지 않으므로
그래야 맞다.

### 5. 같은 근거가 다섯 번 나왔다

`loop error` 로 조회했더니 근거 5 칸이 같은 문장으로 채워졌다.

System Error — The instrument has encountered a system error.

**검색이 그것을 안 보고 서른여섯 건을 각각 후보로 다뤘다.** 어휘도
벡터도 본문이 같으니 점수가 같고, 결과가 같은 문장으로 채워진다.

접기 전: Modbus Map / System Error / System Error / System Error / System Error
접기 후: Modbus Map / System Error (코드 4000~4400 · 36종 공통 설명) / System Error / Modbus Map / Modbus Map

**접되 숨기지 않는다.** 서른여섯 개 중 하나만 보여주면서 그 사실을

### 6. 배포 — Dockerfile 의 죽은 단계

`App.jsx` 를 고쳤는데 배포 화면에 반영되지 않아 Dockerfile 을 다시 읽었다.

```dockerfile
FROM node:20-slim AS ui
RUN npm run build                        # 여기서 빌드한 것이

COPY ui/react/dist/ ./ui/react/dist/     # 여기선 안 쓰인다
```

`--from=ui` 가 없으므로 빌드 컨텍스트(= 저장소에 커밋된 `dist/`)에서
복사한다. 1 단계는 시간만 쓰고 버려진다. 8/23 에 "node 빌드 단계 자체를
제거" 하기로 했는데 단계가 남아 있었다.

지금은 커밋된 `dist/` 를 쓰는 방식이 의도이므로 **시연 전에는 손대지
않는다** — 빌드 경로를 바꾸면 배포가 새로 깨질 여지가 생긴다.
대신 `App.jsx` 를 고칠 때마다 `npm run build` 후 `dist/` 를 커밋해야
한다는 것을 절차로 못박았다. 마감 후 `COPY --from=ui` 로 정리한다.

**저장소 비공개 전환** — 제출 안내의 "외부 저장소는 반드시 비공개" 규정에
따라 Private 으로 바꿨다. Railway 는 이미 연결된 저장소라 배포는 유지됐다.

**API 비용** — 운영측 지원 문의는 하지 않기로 했다(8/22 「남은 것」 철회).
개인 부담으로 간다. 8/23 에 DeepInfra 로 옮기면서 임베딩이 100 만 토큰당
0.01 달러 수준이 되었고 호스팅도 월 5~7 달러 선이라, 문의에 드는 시간이
금액보다 크다. 다만 공개 URL 이므로 사용량 상한은 걸어 둔다.

### 7. 리랭커 측정이 틀렸다 — 8/22 결론 철회

기획서 §7 에 넣을 수치를 확정하려고 데모 구성으로 45 문항 4 구성을

`full` 이 `hybrid` 보다 3 점 높다. 8/22 에 "리랭커는 점수에 기여하지

**원인**

```python
if self.mode == "full" and self.rerank_active and hits:
```

리랭커는 `full` 모드에서만 돈다. `hybrid` 에서는 `COPILOT_RERANK` 를

**무엇을 놓쳤나**

그날도 "설정이 실제로 갈렸는지 의심스러워 두 스코어카드의 실험 조건
줄을 대조했다" 고 적었다. 의심은 맞았는데 확인 대상이 틀렸다. 조건 줄에
찍히는 `rerank=BAAI/bge-reranker-v2-m3` 와 `rerank=off` 는 **설정값이
갈렸다는 뜻이지 적용되었다는 뜻이 아니다.** 봐야 했던 것은 어느 모드에서
잰 값인가였다.

설정을 바꿨는데 점수가 한 칸도 안 움직이면 "효과가 없다" 가 아니라
"설정이 안 읽히고 있다" 를 먼저 의심해야 한다. 이 프로젝트에서 같은
유형으로 세 번 깨졌고(임베딩 캐시 신원 · 챗봇 제공자 인식 · 강등 가시성)
그래서 `selfcheck` 를 만들었는데, 정작 측정 자체에는 같은 장치를 두지
않았다.

**결정 — 배포판은 그대로 둔다**

3 점(6.7%p)을 얻자고 이미지에 torch 약 2GB 가 들어오고, 호스팅 요건이
512MB 급에서 다시 올라간다. 8/23 에 DeepInfra 로 옮기며 얻은 것을
되돌리는 셈이다.

**바꾸는 것은 결정이 아니라 서술이다.** "기여가 0 이라 뺐다" 가 아니라
"3 점을 주지만 배포 비용 대비 효율이 낮아 뺐다" 로 적는다. 전자는

`full 31/45(로컬, 리랭커 포함)` 와 `hybrid 28/45(배포 구성)` 를 둘 다

### 1. 인터락 입력 기준 조회가 껍데기였다

화면에서 「입력 태그 기준 조회」를 체크하면 동작 셀렉트만 비활성화되고
**태그 목록은 출력 태그 그대로였다.** `LCV-01 · 출력`이 남은 채로 입력
기준 조회를 하니 빈 결과가 나왔다. 필터가 탭만 보고 걸렀기 때문이다.

**종류(계기/출력)로 거르면 안 되는 조회다.** 인터락 조건에 등장하는
태그를 세어 보니 34건 중 계기 19 · **출력 11** · 어느 목록에도 없는 것
4(AIT-6004, FIT-5006, LIT-7003, TIT-5005)였다. 펌프가 도는 상태가 밸브
개방의 조건이 되는 식으로 출력 장비가 입력 조건에 들어온다. 계기만
남기면 "펌프를 세우면 뭐가 영향받나"를 못 묻는다.

그래서 서버가 실제 조건을 훑어 `in_interlock` 표시를 내려주고 화면이
그것으로 거르게 했다. 인터락에만 등장하는 4건은 목록에 새 항목으로
추가했다 — 빼면 화면에서 조회할 방법이 없는 조건이 생긴다.

입력 기준일 때는 `· 출력` 라벨을 뗐다. 출력이 섞여 있는 것이 정상인데
라벨이 붙어 있으면 잘못 걸러진 것처럼 읽힌다. 계기 리스트에 없는
태그는 제조사·모델 칸이 비므로 `· ` 만 남던 것도 정리했다.

`useEffect` 의존성에 체크박스 상태를 넣는 것을 빼먹으면 목록이 즉시
안 바뀐다 — 이번 버그의 절반이 그것이었다.

실패 8건을 갈랐다: 검색 실패 3(정답은 색인에 있음) · 정답 표기 불일치
2(기대한 섹션명이 색인에 없음) · **거절 실패 3(전부 답을 만들어냄)**.

**진단이 한 번 뒤집혔다.** 처음에는 원인을 한국어→영문 구간으로
판단했다. 검증 담당이 같은 문항을 영문으로 다시 물은 대조군을 따로
만들었는데(한국어판은 원본 보존), **영문판도 2/10 — 동일했다.**

어휘만 바꿔 확인하니 갈리는 곳이 드러났다.

| 질의 | 결과 |
|---|---|
| "산 시약 통이 거의 바닥나서" (한) | 실패 |
| "Acid reagent bottle is almost empty" (영) | 실패 |
| "acid container volume less than 10%" (영) | 도달 |
| "산 잔량 10% 미만 경고" (기존 평가셋, 한) | 도달 |

**언어가 아니라 원문 어휘를 얼마나 그대로 쓰는가가 가른다.** 기존
45문항의 한국어가 매뉴얼 원문 구조를 따라 쓰여 있었고, 그것이 62% 를
만들었다. 다국어 임베딩은 언어는 넘는데 바꿔 말하기는 못 넘는다.

대조군은 낮은 점수를 본 뒤에 만든 측정이므로 성능 수치로 쓰지 않고
두 판의 차이만 읽는다고 보고서에 명시했다(`docs/홀드아웃_검증결과.md`).

**부수 수확** — 채점 1회차에서 채점은 끝났는데 스코어카드 저장에서
죽었다. `write_md` 가 `meta["fairness_note"]` 를 필수로 읽는데 홀드아웃
템플릿에는 없다. 한 번만 채점하는 규칙 때문에 결과가 통째로 날아갈 뻔
했다. 없어도 돌게 고치고, 스코어카드에 **작성자**를 함께 찍게 했다 —
같은 점수라도 누가 만든 문항인지에 따라 뜻이 다르다.

### 3. 청킹 소제목 가설 — 측정으로 기각

홀드아웃 body 실패를 파다가 원인 후보를 찾았다. M9e 매뉴얼의 책갈피는
244개인데 `Step 5: Install the DI Water System` 같은 실제 소제목이
책갈피에 없어서, 11페이지 구간의 청크 18개가 전부 같은 제목을 달고
있었다. 제목은 bm25·dense 모두 본문 앞에 붙여 쓰므로 신호가 뭉개진
상태다 — 그럴듯한 가설이었다.

페이지 안의 소제목을 폰트 크기·굵기로 찾아 붙였다. 장 머리글
(`INSTALLATION` 이 매 페이지 18pt 로 반복)이 제목으로 잡히는 것은 문서
전체 3회 초과 반복으로 걸렀고, 책갈피 제목은 지우지 않고 덧붙였다 —
갈아치웠더니 `Bubbles in Reagent Lines` 처럼 원래 정확하던 제목이
사라져 기존 문항이 깨졌다. 고유 제목 403→499, 최대 섹션 60→43청크.

**측정 결과가 반대로 나왔다.**

| | 기존 | 소제목 청킹 |
|---|---|---|
| 45문항 | 28/45 | 27/45 |
| — body | 5/9 | 4/9 |
| 홀드아웃 | 2/10 | **0/10** |

홀드아웃 syn 이 2→0 인 것이 원인을 말해 준다. syn 은 코드표를 찾는
문항이고 코드표는 한 글자도 안 바뀌었다. 즉 **길고 다양해진 본문
제목이 코드표 항목을 순위에서 밀어냈다.** 변별력을 올리려던 것이
잡음을 올렸다. 원복했다.

가설이 그럴듯할수록 측정 없이 채택하고 싶어진다. 이번 것은 코드를
다 만들고 색인까지 두 번 다시 지은 뒤에야 기각됐지만, 그 비용이
"채택하고 나서 모르는 것" 보다 싸다.

### 4. 페이지 인용이 3건 중 1건 어긋나 있었다

청킹을 들여다보다 별개 결함을 찾았다. `pdf_page` 가 실제 페이지가
아니라 **구간 길이에 비례한 근사값**이었다. M9e 645청크를 전수
대조하니 정확 68%, 두 쪽 이상 어긋남 68건, 최대 17쪽.

제시하는 것이 이 도구의 핵심인데, 눌러서 다른 내용이 나오면 근거를
댔다고 할 수 없다.

청크 앞 40자를 구간 안 페이지 본문과 대조해 실제 페이지를 찾도록

정확해졌고**, 청크 본문·제목·경계가 그대로라 검색 점수는 바이트
단위로 동일했다(28/45, O/X 일치). 측정 과정에서 처음에 문서 전체를
훑는 바람에 목차 페이지에 먼저 걸려 "최대 404쪽 오차" 라는 엉터리
수치가 나왔는데, 구간 안으로 한정하니 바로잡혔다 — 측정 도구부터
의심할 것.

### 5. 거절 시 모델 추측 — 격리가 기능의 전부다

근거를 못 찾으면 화면이 통째로 비고, 현장에서는 그 순간 도구를 닫는다.
그래서 abstain 일 때 모델 추측을 붙이기로 했다. **다만 이 기능의
값어치는 추측의 품질이 아니라 격리에 있다.** 근거 있는 답과 추측이
같은 무게로 보이는 순간 "근거 없이 답하지 않는다" 는 전제가 무너진다.

격리 장치 네 겹:
- abstain 판정에서만 생성, advise 에는 절대 미부착
- 조치 배열(steps)에 넣지 않고 별도 필드 — 4D 리포트가 못 읽는다
- 화면은 기본 접힘 + 「매뉴얼 근거 없음 · 모델 추측」 라벨 + 경고문
- 출력에 문서명·페이지·"매뉴얼에 따르면"·근거 번호가 섞이면 통째 폐기

selfcheck 에 「추측 격리 [주입]」을 추가했다(41번째). advise 미부착 ·
steps 분리 · 리포트 미포함 세 가지를 재고, 일부러 steps 에 섞어 넣으면
검출하는 것까지 확인했다.

**침묵 실패를 한 번 저질렀다.** 처음 구현이 `except: return None` 으로
조용히 넘어가서, 화면에 아무것도 안 뜨는데 원인을 알 수 없었다. 이
프로젝트는 검색 강등도 사유를 화면에 남기는데 새 기능만 그 방침을 안
따랐다. `(결과, 사유)` 를 돌려주고 안 나온 이유를 화면에 찍게 고쳤다.
품질은 검증할 방법이 없으므로(정답 없는 출력) 수치를 주장하지 않는다 —
검증 가능한 것은 규칙으로, 불가능한 것은 격리된 참고로.

### 1. 추측을 모든 조회에서 볼 수 있게 — 다만 모드로 가른다

어제 만든 모델 추측은 거절(abstain)에서만 나왔다. "확실하지 않아도
사용자가 보고 싶을 때가 있다" 는 요구가 나왔는데, 근거를 찾은 조회에
그냥 붙이면 근거 있는 답과 추측이 같은 무게로 보인다. 그러면 "근거
없이 답하지 않는다" 는 전제가 무너진다.

**모드로 갈랐다.** 사용자가 명시적으로 고른 상태라면 무엇을 보고
있는지 아는 것이고, 그 위험이 사라진다.

- 근거 모드(기본) — 지금까지 동작 그대로
- 자유 모드 — 근거를 찾은 조회에도 추측이 함께 뜨고, 도우미가 문서 밖
  질문에 일반 지식으로 답한다

**모드와 무관하게 지키는 선 셋을 먼저 정하고 만들었다.** 추측은
steps 에 섞이지 않는다(섞이면 조치로 저장되어 다음 조회의 이력 근거가
된다), 4D 리포트에 실리지 않는다(결재를 탄다), 라벨은 항상 붙는다.
selfcheck 「추측 격리」에 자유 모드 검사를 더해 이 셋을 재게 했다.

자유 모드는 새로고침하면 꺼진다. 저장하지 않는 것이 의도다 — 어느
모드인지 모른 채 화면을 보는 상황이 가장 위험하다.

**추측은 검색 결과를 참조하지 않는다.** 이 결정을 다시 확인했다.
abstain 은 아무것도 못 찾은 상태가 아니라 찾았는데 충분성이 문턱에
미달한 상태다. 그 약한 근거를 추측 프롬프트에 넣으면 모델이 그것으로
그럴듯한 문장을 만드는데, 이 경로에는 인용 검증이 없다. **검증 안 된
근거가 문장으로 세탁되어 나오는 셈이다.** 근거를 쓰는 답은 인용
검증을 거친 조치 경로 하나뿐이고, 추측은 근거를 아예 보지 않아
「문서 근거 아님」 라벨이 사실이 된다. 반쯤 참조하면 라벨이 거짓이 된다.

---

### 2. 자유 모드가 챗봇에서 동작하지 않았다 — 두 번 고쳤다

**첫 번째.** 자유 모드를 켜고 도우미에게 물었는데 "근거에 기반한
답변을 만들지 못했습니다" 로 끝났다. 근거 QA 경로가 먼저 잡는데,
**실패해도 그 실패 답변을 그대로 반환**하고 있어 자유 경로까지 가지
못했다. 자유 모드일 때만 실패 시 다음 경로로 넘어가게 했다.

**두 번째.** 그래도 어떤 질문은 답이 없었다. 화면을 보니 알람 문구
칸이 질문 문장으로 바뀌어 있었다 — 규칙이 그 입력을 **조회 명령**으로
해석해 실행한 것이다. 즉 QA 경로가 아니라 조회 후속 경로였고, 내가
고친 자리가 아니었다. 후속 경로는 우회해도 같은 QA 를 다시 돌려 같은
실패를 반복한다.

**넘기는 대신 덧붙이는 방식으로 바꿨다.** 근거로 답하지 못하면 그
사실을 그대로 두고 뒤에 모델 답변을 붙인다.

```
매뉴얼에서 근거를 찾지 못했습니다. 1위가 매뉴얼 본문, 벡터 유사도 0.52…

〔모델 답변 · 문서 근거 아님〕
에어락은 배관이나 펌프 내부에 공기가 갇혀 유체 흐름이 막히는…
```

**근거 없음을 지우지 않은 것이 요점이다.** 자유 모드를 켠 뜻은
"근거가 없어도 참고할 것을 달라" 이지 "근거 없음을 감춰 달라" 가
아니다. 둘 다 보여야 사용자가 무엇을 믿을지 스스로 정한다.

자유 답변에도 추측과 같은 폐기 기준을 걸었다 — 문서명·페이지·
"매뉴얼에 따르면"·근거 번호가 섞이면 통째로 버린다. 프롬프트에는
조회 결과(판넬 위치·인터락 조건·페이지)를 지어내지 말고 해당 조회
기능으로 안내하라고 명시했고, 실제로 "특정 설비(AIT-4002)의 에어락
여부나 조치 절차는 매뉴얼 조회 기능으로 확인하실 수 있습니다" 로
동작했다.

**같은 질문에 두 모드가 이렇게 갈린다.**

| 모드 | 답 |
|---|---|
| 근거 모드 | "매뉴얼에서 근거를 찾지 못했습니다" + 못 찾은 사유 + 근거 3건 |
| 자유 모드 | 위와 같고, 뒤에 라벨 붙은 일반 지식 설명이 이어짐 |

---

### 3. 화면 — 버튼 길이가 레이아웃을 흔들었다

모드 토글의 라벨 길이가 모드마다 달라(「근거 모드 (기본)」 /
「자유 모드 — 근거 없는 내용 포함」) 줄바꿈이 생기고 아래 메뉴가
밀렸다. 라벨을 네 글자로 맞추고 높이를 고정했다.

자유 모드 안내는 본문 상단 띠에서 **제목 옆 배지**로 옮겼다. 띠는
본문을 밀어내는데, 모드는 늘 켜져 있을 수 있는 상태이므로 자리를
차지하지 않아야 한다. 배지는 알람·판넬·인터락 세 화면에 모두 붙였다 —
모드는 챗봇 포함 전 화면에 걸리는데 알람에만 두면 다른 탭에서 켜져
있는 줄 모른 채 쓰게 된다.

---

### 4. 배치 경로 고정 — 세 번 반복한 사고를 이제야 막았다

`run_eval.bat` 과 `run_check.bat` 은 실물 자료용인데 **경로를 설정하지
않고 기본값에 기대고 있었다.** 그래서 데모 변수가 살아 있는 창에서
실행하면 그 값을 물려받는데, 화면에는 `DATA = ...\data` 라고 찍혔다.
**표시가 사실과 달랐다.** 어제 데모 색인이 실물 매뉴얼 45종으로 덮인
사고가 이 구조에서 나왔다.

네 파일로 정리했다.

| 파일 | 대상 |
|---|---|
| `run_eval.bat` · `run_check.bat` | 실물 — 경로를 명시적으로 못 박음, echo 가 실제 변수값 표시 |
| `run_eval_demo.bat` (신규) | 제출 수치 측정 — 45문항·홀드아웃·인터락 일괄 |
| `run_rebuild_demo.bat` (신규) | 색인 재구축 — 경로를 찍고 `pause`, 확인 후 Enter 를 눌러야 진행 |

색인 재구축은 되돌리기 가장 비싼 작업이다. 측정은 잘못돼도 다시 재면
그만이지만 색인은 임베딩까지 다시 만들어야 한다. 그래서 그 하나만
확인 절차를 두었다.

**8/23 일지에 "환경변수가 세션마다 풀려 같은 실수를 네 번 반복했다"
고 적고도 배치를 만들지 않았다.** 기록하는 것과 고치는 것은 다른
일이라는 것을 이번에 배웠다.

### 5. 잔손질

챗봇 창 높이를 드래그로 조절하게 했다. 근거 인용이 붙은 답변은 길어서
기본 높이로는 답 하나를 보려고 계속 스크롤해야 했다. 한도(320~900px)를
두고, 두 번 누르면 기본 크기로 돌아간다.

도우미 아이콘을 바꿨다. 처음 쓰던 이미지가 다른 회사 AI 로고와 형상이
비슷해 보인다는 지적이 있었다. 이미지 파일 대신 도형(SVG)으로 그렸다 —
파일이면 배경 여백이 따라와 어두운 화면에서 흰 테두리가 생기고, 크기마다
다시 만들어야 한다.

이 과정에서 창 크기·위치·글자 크기 조절과 아이콘 접기까지 만들어 봤으나
**전부 되돌렸다.** 마감 8일 전에 조작 방식을 여섯 가지나 바꾸면 시연
중에 무엇이 튀어나올지 모른다. 쓰면서 불편한 점은 고치지 않고 기록만
남기기로 했다 — 결선 준비 재료로 쓴다.
