# 시연 시나리오 — SCADA 알람 2단계 진단 (패치 27 기준)

작성 2026-08-27. 아래 수치는 전부 **데모 세트 · lexical 모드 실측**입니다.
hybrid(배포 환경)에서는 순위가 달라질 수 있으므로, 시연 전 같은 입력으로
한 번씩 눌러 보고 화면 값을 이 문서에 덧적어 두십시오.

## 왜 2단계인가 (심사 답변용 한 문단)

SCADA가 원격으로 보내는 알람은 HH / LL / LOOP ERROR / ON·OFF COMMAND와
카드 SSL 진단 코드뿐입니다. 그런데 이 어휘는 벤더 매뉴얼에 **0건**입니다
(색인 전수 검색 실측: "loop error" 0건, "high high" 0건, "low low" 0건).
알람은 상태를 말하고 매뉴얼은 절차를 말하기 때문입니다. 그래서 이 도구는
1단계(원격)에서 원인을 확정하지 않고 **현장에서 확인할 항목**을 내놓으며,
2단계(현장 확인 입력)에서 근거가 좁혀지면 그때 원인을 싣습니다.
근거가 얇은 단계에서 얇다고 말하는 것이 설계입니다.

## 장면 1 — 원격: LOOP ERROR 접수

입력: 태그 `AIT-4002` · 알람 문구 `LOOP ERROR` · 계기 화면 코드 (비움)
(소문자 `loop error`도 동일하게 라우팅됩니다 — 27b에서 대소문자 무시로
넓힘. 시연 중 어느 쪽으로 쳐도 됩니다. 축약형 HH/LL만 대문자.)

실측(hybrid — 2026-08-27 현장 확인):
- 판정 **advise · 충분성 0.93**, 1위가 매뉴얼 본문, 어휘·벡터 검색 합의
- trace 2줄째: `alarm-route: LOOP — 확장 [wire break, supply voltage missing,
  will not power on, fuse, underrange, 4-20 mA] · 카드 제한 해제`
  → 알람명을 사전에 박은 것이 아니라 **카드 진단표·트러블슈팅 표제어로
  확장**했음을 화면 trace가 직접 보여줍니다. 심사에서 이 줄을 짚으십시오.
- 근거 5건 구성 — 카드 4 + 계기 1:
  1. **ET200SP `Supply voltage missing`** (p.54 Table A-1) — 카드가 본 것
  2. C.4 4-20 mA 측정 범위 이상값(32767/7FFF)
  3. 전력 공급 모니터링·오버로드 (p.18)
  4. 5.3 모듈·채널 파라미터 — failure monitoring 3.6~21 mA (p.20)
  5. **M9e p.274 The Analyzer Will Not Power On** — 계기 쪽 원인 후보
  → `_cap_card`의 계기 근거 1건 확보가 작동한 결과입니다. "카드가 신호
  상실을 감지했고, 계기 쪽 원인 후보는 이것"이라는 두 축이 한 화면에 섭니다.
- 하단 경고 줄: "현장 이력이 매뉴얼과 다른 원인을 기록한 사례가 있습니다
  (불일치 1 / 일치 1 / 부분일치 3)" — 매뉴얼이 원인 후보를 주고, 현장은
  그와 다른 결말을 낸 적이 있다고 도구가 스스로 말합니다. 짚고 넘어가십시오.
- 응답 `card_siblings`: 카드 `RIO-01/DP11/R0/S8`, 동반 태그
  `AIT-2002, AIT-3002, FIT-2004, FIT-2009` — 4D PDF의 D2에
  "※ 동일 카드 동반 태그 … 동시 알람 시 카드 공통 원인 우선 점검" 줄로 실림

참고(lexical): advise 0.53. 상위 2건이 설치 절차 문서로 잡히는 잔여
노이즈가 있고 p.274는 3위입니다. hybrid 쪽이 확연히 깨끗합니다.

말할 것: "원인은 아직 확정하지 않습니다. 현장에서 확인할 것 — 계기 전원
표시, 화면 코드, 단자대 전압, 배선 상태."

## 장면 2 — 현장: 계기 화면이 꺼져 있음

입력: 태그 `AIT-4002` · 알람 문구 `no power` (계기 화면이 아예 꺼져 있어
화면 코드는 없음 — 꺼진 장비는 코드를 못 냅니다. M9e 코드표에 '전원 없음'
코드가 없는 이유이기도 합니다.)

실측(hybrid — 2026-08-27 현장 확인):
- 판정 **advise · 충분성 1.00**
- trace에 `alarm-route` 줄이 **없습니다 — 정상입니다.** `no power`는
  알람명이 아니라 현장 증상이라 라우팅 대상이 아닙니다.
- 근거: M9E-10055 / M9E-10057(power cycle 계열 공통 설명) 다음
  **3위에 M9e p.274 The Analyzer Will Not Power On** — 퓨즈 교체 절차까지
  본문에 실려 나옵니다. 4위 Installing the Power Source.
- lexical에서는 p.274가 1위입니다. hybrid에서는 dense가 "no power"를
  시스템 에러 문구 쪽으로 당겨 3위로 내려갑니다. 화면 안에 있으므로 시연에
  지장은 없고, **순위 튜닝은 하지 않습니다**(데모 맞춤 금지 원칙).

말할 것: "정보가 늘자 같은 도구의 답이 좁혀졌습니다. 1단계에서 미리
말하지 않은 것이 틀린 게 아니라 정직한 겁니다."

이력 연결:
- **실물 세트**: 확정 원인 사슬이 이력 WO-2026-029(전원케이블 단선)로
  닫힙니다. 시연을 실물 세트로 하면 이 WO가 이력 카드에 뜨는지 사전 확인.
- **데모 세트**: AIT-4002에 전원 계열 이력이 없습니다(WO-2026-004 산 잔량
  오산정 · WO-2026-010 리드선 접촉 불량 등). 데모 세트로 시연하면 이력은
  "유사 증상 없음"으로 두고, 4D의 확정 원인은 조치 저장(FeedbackForm)으로
  기입하는 흐름을 보여주십시오 — 어느 쪽이든 지어내지 않는 그림입니다.

마무리: 4D 리포트 PDF 출력 — D2에 동반 태그 줄, D3에 p.274 근거, 매뉴얼
근거가 없는 조회에서는 "• 매뉴얼 근거: 없음 — …(이력 기준으로 판단)"이
명시됩니다.

## 장면 3 — 알람 폭주: 카드가 죽으면 5개가 같이 운다

배경: AIT-4002는 RIO-01/DP11/R0/S8 카드에 AIT-3002 · FIT-2009 · AIT-2002 ·
FIT-2004와 동거합니다. 카드가 죽으면 5점이 동시에 LOOP ERROR를 냅니다.
이때 개별 태그 조회는 다섯 번 다 오답입니다 — 진짜 원인은 카드 1장.

실행(터미널 또는 브라우저):

```
GET /api/common-cause-of?tags=AIT-4002,AIT-3002,FIT-2009,AIT-2002,FIT-2004
```

실측 응답(요지):

```json
{"known": 5, "unknown": [], "level": "card", "node": "RIO-01/DP11/R0/S8",
 "note": "동시 알람 5점이 모두 카드 RIO-01/DP11/R0/S8 소속 — 카드 공통
 원인(전원·백플레인·카드 자체)을 개별 계기보다 먼저 점검. SSL 진단(11H 등) 확인.",
 "uncovered": []}
```

이어서 SSL 코드 확인: 알람 문구에 `11H`를 넣으면 코드 완전일치(exact)로
ET200SP **11H Supply voltage missing**이 뜹니다(패치 27에서 16진+H 코드
조회 수정). `8H`(Low limit violated)도 동일.

**반례 시연도 준비돼 있습니다** — 태그를 하나 빼고(4개만) 같은 URL을
부르면 판정은 `card`를 유지하면서 응답에
`"uncovered":["FIT-2004"]`, note에 "같은 카드의 미알람 태그 FIT-2004
상태가 반례가 될 수 있음 — 함께 확인"이 붙습니다(2026-08-27 실측).
"모른다"와 "반례"를 구분한다는 것이 한 화면에 드러나는 장면입니다.

판정은 4계층입니다: 같은 카드(card) → 같은 랙(rack) → 같은 판넬(panel) →
같은 PLC → 흩어짐(scattered). 색인에 없는 태그는 `unknown`으로 분리합니다.

주의: 이 화면은 UI에 없습니다(빌드된 dist 미수정). API 응답 JSON을 그대로
보여주거나, 시연 영상에서는 브라우저 주소창으로 찍는 것이 자연스럽습니다.
