## 문제

기획서 6-3이 식별한 두 지점. 둘 다 "단계가 여럿이고 다음 행동이 앞
결과에 따라 갈리는" 작업이라 사람이 반복하고 있었다.

**① 반입 점검이 짚은 것을 사람이 고친다.** 점검 리포트가 지적을 내면
사용자가 엑셀을 열어 고치고 다시 올리는 왕복. 지적이 수십 건이면 실제
부담이고, 고치는 중에 새 실수(falsy-zero 같은)가 들어갈 수 있다.

**② 동시 알람 조사를 사람이 다섯 번 누른다.** 카드 한 장이 죽으면 물린
계기 전체가 알람을 내고, 그때 개별 태그 조회는 전부 오답이다. 공통 조상
판정 → 반례 확인 → 코드 근거 → 종합의 절차가 정해져 있는데 화면에는
없었다 (`common-cause-of` API만 있었음).

## 무엇을

### ingest/repair.py — 수리안 제안·반영

- `propose()` — 읽기만. 제안 종류:
  - `channel_dup` (자동) — 같은 카드·같은 CH 의 동거를 같은 슬롯의 빈
    채널로 재배정. **CH=0 은 유효값** — `is None` 검사만 쓴다.
  - `header_rename` (자동) — 표준 24종과의 근사 일치(difflib 0.75)로
    헤더 오기 복원.
  - `header_missing` / `tag_mismatch` (수동) — 후보만 보이고 반영하지
    않는다. 문서 사이 의미가 걸린 것은 자동화하지 않는다.
- `apply(ids)` — 클라이언트 내용을 믿지 않고 **서버가 제안을 새로 계산해
  id 일치만 반영.** 반영 전 `.prev` 보존(반입 관례), 반영 후 재점검
  수치를 돌려준다 — 고쳐졌는지를 말이 아니라 수치로.

### retrieval/flood.py — 조사 오케스트레이션

`investigate(tags, codes?, alarm?)` — 6단계를 밟고 **전 단계를 steps 로
남긴다**: 공통 조상 판정(판넬 색인) → 미알람 동반 태그(반례) → 태그
소속 대조 → 코드 근거(코드 완전일치) → 알람명 근거(선택) → 결론 조립.
결론은 규칙 조립이며 **LLM 을 쓰지 않는다** — 같은 입력에 같은 보고.
자율성은 "어느 조회를 부를지"에 한정되고 각 조회는 검증된 계층이 답한다.

### API (api/server.py — 추가만)

- `GET /api/ingest/repair-plan` — 읽기, 열쇠 불필요
- `POST /api/ingest/repair-apply` — `_require_edit` (열쇠·임대), 반영 후
  판넬 캐시 무효화
- `GET /api/investigate-flood?tags=&codes=&alarm=` — 읽기

### 화면 (ui/react/src/App.jsx)

- 반입 화면에 「수리안」 패널 — 체크박스로 골라 반영, 자동 항목만 선택
  가능, 수동 항목은 후보 표시만. **전체 자동 반영 버튼은 만들지 않았다.**
- 판넬 화면에 「동시 알람 조사」 패널 — 태그·코드 입력, 단계·결론·코드
  근거 표시. SCADA 미연결이라 태그는 사람이 넣는다고 화면에 명시.

### 가드 3종 (eval/selfcheck.py)

- `수리안 왕복 [주입]` — 중복 2(CH=0 포함)·헤더 오기 1을 픽스처에 심고
  제안 3건 → 반영 → 재점검 0건, `.prev` 존재, **원본 무손상**(md5).
- `수리 반영 열쇠 [주입]` — 무열쇠 401 / 유열쇠 통과.
- `동시 알람 조사 [주입]` — 4태그+11H 로 card 판정·반례(FIT-2004) 명시·
  코드 근거·5단계 이상 기록.
