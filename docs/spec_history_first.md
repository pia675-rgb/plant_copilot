# 이력 우선 조치 규칙 (History-First Advisory)

**목적** — 조치 순서 생성에 현장 보수 이력을 반영한다. 특히 매뉴얼과 다른 실제 원인이 기록된 이력이 있으면, 매뉴얼이 지시하는 조치보다 먼저 제시한다.

**설계 원칙** — 규칙으로 결정하고 LLM은 문장만 다듬는다. 이력 카드의 존재 여부와 순서는 결정적이어야 하며, LLM이 지시를 놓쳐도 카드는 살아 있어야 한다.

---

## 1. 매칭 규칙

### 1-1. 입력

| 값 | 확보 방식 | 확실성 |
|---|---|---|
| `tag` | 사용자가 직접 입력 | **항상 확보** |
| `symptom_query` | 사용자가 한글로 입력한 증상 | **항상 확보** |
| `device` | Instrument List 에서 `tag` 로 조회 (MODEL) | **항상 확보** |
| `code_ref` | 검색 결과 중 `kind == "error_code"` 의 `code` | 검색 성공 시에만 |

**핵심 판단** — 실제 사용에서 사용자는 알람 코드를 입력하지 않고 증상만 한글로 씁니다. 따라서 `code_ref` 를 매칭의 축으로 삼으면, 검색이 코드표를 집지 못하는 순간 이력 기능 전체가 죽습니다. **검색 정확도에 이력 기능을 종속시키지 않습니다.**

`code_ref` 는 축이 아니라 **가산 신호**로만 씁니다. 잡히면 점수를 더하고, 없어도 규칙은 그대로 동작합니다.

### 1-2. 증상 유사도

이력의 `symptom` 필드는 전부 한글입니다. 질의도 한글입니다. **한글 대 한글 매칭이므로 매뉴얼 검색이 겪는 한글→영문 문제가 없습니다.** 임베딩 없이 어휘 기반으로 충분하고, 대상이 수십 건 규모라 비용도 사실상 없습니다.

```
sim(query, symptom) = 어휘 겹침 기반 점수 (BM25 또는 토큰 자카드)
```

같은 입력에 항상 같은 결과가 나오는 **결정적 함수**여야 합니다. 채점 가능성이 여기에 달려 있습니다.

임계값은 데이터로 정합니다. 이력 29건의 `symptom` 을 질의로 넣었을 때 자기 자신이 1위로 잡히고 무관한 건이 안 딸려오는 지점을 찾아 고정합니다. **임계값을 평가셋에 맞춰 조정하지 않습니다.**

### 1-3. 3단 매칭

우선순위 순이며, 상위 단계에서 걸린 이력은 하위에서 중복 수집하지 않습니다.

| 단계 | 조건 | 의미 | 검색 의존 |
|---|---|---|---|
| **L1** | `tag` 일치 **AND** 증상 유사도 ≥ 임계 | 이 계기에서 이 증상이 재발 | 없음 |
| **L2** | `tag` 일치 (증상 무관) | 이 계기의 다른 이력 | 없음 |
| **L3** | `device` 일치 **AND** 증상 유사도 ≥ 임계 (tag 불일치) | 같은 기종 다른 계기의 동일 증상 | 없음 |

**세 단계 모두 검색 결과를 필요로 하지 않습니다.** 태그와 증상과 기종만으로 결정됩니다.

`code_ref` 가 잡힌 경우, 이력의 `code_ref` 와 일치하면 해당 이력의 정렬 우선순위를 올립니다. 수집 여부 자체는 바꾸지 않습니다.

**L3에 `device` 조건을 붙이는 이유** — 증상 문구는 기종이 달라도 비슷하게 쓰입니다("유량 미검출" 등). 기종까지 같아야 같은 고장으로 봅니다.

### 1-4. 제외 규칙

- `device` 만 일치하고 증상이 다른 이력은 **수집하지 않습니다.** 같은 기종이라는 이유만으로 무관한 고장을 끌어오면 노이즈가 됩니다. 현재 데이터에서 M9e 가 16건이라, 이 조건이 없으면 M9e 태그 질의마다 무관한 이력이 대량으로 딸려옵니다.
- 각 단계 내 최대 3건, 전체 최대 5건.

### 1-5. 정렬

각 단계 안에서 다음 순으로 정렬합니다.

1. `manual_match == "불일치"` 우선
2. `code_ref` 가 잡혔고 일치하는 건
3. `manual_match == "부분일치"`
4. `date` 최신순

**불일치를 최우선으로 두는 것이 이 규칙의 핵심입니다.** 매뉴얼대로 해서 안 됐던 기록이 가장 값어치 있는 정보입니다.

## 2. 출력 — 이력 카드

### 2-1. 삽입 위치

조치 순서 배열의 **맨 앞**. LLM이 생성한 단계들보다 앞선다.

### 2-2. 등급

| 등급 | 조건 | 화면 표시 |
|---|---|---|
| **경고** | 수집된 이력에 `불일치` 포함 | 매뉴얼과 다른 원인이 기록된 사례가 있습니다 |
| **참고** | `부분일치` 만 포함 | 유사 사례가 있습니다 |
| **확인** | `일치` 만 포함 | 매뉴얼과 같은 원인으로 처리된 사례가 있습니다 |
| 없음 | 수집 0건 | 카드 미표시 |

### 2-3. 카드 내용

각 이력마다 다음을 표시한다. 원문 그대로 옮기며 요약하거나 재서술하지 않는다.

```
[H1] 2025-04-08 · PIT-1010 · 채널 단선 진단 (Wire break)
     매뉴얼 대조: 불일치
     처음 조치: 배선 점검 (이상 없음)
     실제 원인: 미사용 채널이 Disable 되지 않아 단선으로 진단됨
     최종 조치: 미사용 채널 Disable 처리 · 40분 · 담당 P.C.
     매칭 근거: L1 (동일 태그 · 증상 일치)
```

**매칭 근거를 반드시 표시한다.** 왜 이 이력이 나왔는지 보이지 않으면 사용자가 신뢰하지 못한다. L3(다른 태그)인 경우 특히 필요하다.

## 3. LLM 연계 (2단계)

규칙 카드가 동작한 뒤에 얹는다.

### 3-1. 프롬프트 추가

`_prompt(tag, alarm, evidence)` 에 이력 절을 추가한다. 근거 번호는 `[1] [2]`, 이력 번호는 `[H1] [H2]` 로 구분한다.

### 3-2. 프롬프트 규칙 추가

```
- 현장 이력 중 "매뉴얼 대조: 불일치" 인 건이 있으면, 매뉴얼 근거가
  지시하는 조치를 첫 단계로 쓰지 마십시오. 이력에 적힌 실제 원인을
  먼저 확인 항목으로 올리십시오.
- 이력을 근거로 쓴 단계는 [H1] 처럼 이력 번호를 표기하십시오.
- 이력에 없는 내용을 이력인 것처럼 쓰지 마십시오.
```

### 3-3. 검증 로직

`resolve()` 가 `H` 접두 번호를 통과시키도록 확장한다. 존재하지 않는 이력 번호를 참조한 단계는 기존 `dropped` 규칙대로 버린다.

## 4. 평가셋 설계

`eval/make_eval_history.py` — 이력 데이터에서 문항을 자동 생성한다.

### 4-1. 문항 유형

| 유형 | 검사 내용 | 정답 판정 | 문항 |
|---|---|---|---|
| `l1_hit` | 동일 태그·유사 증상 이력이 카드에 나오는가 | 해당 `wo_no` 포함 | 29 |
| `l3_cross` | 같은 기종 다른 태그의 유사 증상 이력이 나오는가 | 해당 `wo_no` 포함 | 22 |
| `sort_rule` | 유사도가 같을 때 불일치 이력이 최상단에 오는가 | 첫 항목의 `wo_no` 일치 | 1 (합성) |
| `grade` | 등급 판정이 맞는가 | 경고/참고/확인 일치 | 29 |
| `no_leak` | 무관한 태그에 남의 이력이 새지 않는가 | 카드 미표시 | 10 |
| `device_guard` | 증상 같고 기종 다른 이력을 배제하는가 | 맞는 기종 포함 **AND** 다른 기종 미포함 | 1 (합성) |
| `no_search` | 검색을 완전히 실패시켜도 카드가 나오는가 | 카드 표시 유지 | 8 |

`no_leak` 과 `device_guard` 는 **부정 문항**이다. 나와야 할 것이 나오는지만 보면 규칙이 과하게 넓어도 만점이 나온다.

**합성 픽스처 2문항** — 현재 자료에 해당 상황이 없어 코드 안의 가짜
레코드로 시험한다. 자료에 상황이 없다는 것이 규칙을 안 재도 된다는
뜻은 아니다.

- `sort_rule` — 불일치 건의 증상으로 물으면 유사도가 1.0 이라 어떤
  정렬을 써도 1위가 된다. 유사도가 같은 상황을 만들어 정렬만 남긴다.
- `device_guard` — 기종이 다른 쌍 500개의 최대 유사도가 0.125 로
  임계(0.35)에 못 미친다. 실데이터로는 device 조건을 지워도 한 문항도
  안 무너진다. 같은 증상 문구를 기종만 달리해 둘 놓고, **수집과 배제를
  한 문항에서 함께** 본다 — 배제만 재면 L3 를 지워도 만점이고, 수집만
  재면 device 조건을 지워도 만점이다.

### 4-2. 변이 시험

점수가 허수가 아님을 확인한다. 인터락·판넬 평가와 같은 방식.

| 변이 | 기대 결과 |
|---|---|
| L3 매칭 제거 | `l3_cross` 전부 실패 · `device_guard` 실패 · `grade` 일부 실패 |
| 불일치 우선 정렬 제거 | `sort_rule` 만 실패 |
| device 조건 제거 | `device_guard` 실패 · `no_leak` 전부 실패 |
| 증상 유사도 무시(전건 수집) | `no_leak`·`device_guard` 전부 실패 |

**곁가지 붕괴는 결함이 아니라 실제 결합이다.** `L3 매칭 제거` 에서
`device_guard` 가 함께 무너지는 것은 그 문항의 수집 쪽 절반이 L3 에
얹혀 있기 때문이고, `grade` 가 떨어지는 것은 L3 로만 이력이 잡히던
태그가 카드를 통째로 잃기 때문이다. 결합을 감추려고 문항을 쪼개면
규칙을 못 가둔다.

정렬 변이만은 한 유형에서 끝나야 한다. 정렬은 수집 범위를 바꾸지
않으므로 다른 유형에 영향이 없어야 맞다.

측정값은 `eval/scorecard_history.md` 에 있다.

### 4-3. selfcheck 추가

고장 주입 검사에 항목을 추가한다.

| 항목 | 주입 | 통과 조건 |
|---|---|---|
| 이력 파일 부재 [주입] | `maintenance_history.json` 을 치운다 | 예외 없이 완주 · 카드 미표시 · 조치는 그대로 |
| 이력 번호 위조 [주입] | `wo_no` 하나를 없는 값으로 바꾼다 | 그 이력을 지목한 문항만 실패 |

**부재 검사는 정상 상태를 먼저 확인한다.** 이력 기능이 통째로 죽어
있어도 "카드가 안 뜬다" 는 항상 참이라, 그것만 보면 아무것도 지키지
못한다. 같은 질의로 카드가 실제로 뜨는 것을 확인한 뒤에 파일을 치운다.
질의 태그·증상은 이력 자료에서 뽑는다 — 코드에 박으면 자료를 바꿔
끼웠을 때 "카드가 안 뜬다" 가 아니라 "태그가 없다" 로 실패한다.

**위조 검사는 채점이 신원을 보는지 본다.** 건수만 세고 있으면 규칙이
엉뚱한 이력을 골라도 만점이 나온다. 무관한 문항까지 무너지는 경우도
실패로 본다 — 문항이 서로 엉켜 있으면 어느 규칙이 깨졌는지 못 가린다.
위조 대상은 가장 많은 문항이 지목하는 `wo_no` 로 고르고, 합성 픽스처
문항은 후보에서 뺀다(자료가 아니라 코드 안의 가짜 레코드를 보므로
위조해도 반응하지 않는다).

## 5. 구현 순서

1. `retrieval/history_index.py` — 3단 매칭 함수. 순수 함수로 두어 테스트를 쉽게 한다 ✔
2. `api/server.py` 743·1693 호출부에서 카드 생성 후 조치 배열 앞에 삽입 ✔
3. UI에 카드 렌더링 (등급별 색상, 매칭 근거 표시) ✔
4. `eval/make_eval_history.py` + 채점 ✔
5. 변이 시험 3종 측정 ✔ (4종으로 늘림 — `eval/scorecard_history.md`)
6. `selfcheck` 2항목 추가 ✔
7. **여기까지 통과한 뒤에** LLM 프롬프트 연계(3절) ✔

7번을 마지막에 두는 이유 — 규칙이 검증된 뒤에 얹어야, LLM 쪽에서 문제가 생겨도 어디가 원인인지 분리된다.
