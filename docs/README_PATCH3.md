# 패치 3 — 결과 구성 다양성

바뀐 파일: `config.py`, `retrieval/pipeline.py` 두 개.

## 무엇을 고쳤나

실패 12문항을 뜯어보니 **전부 `advise`** 였습니다. 임계값 문제가 하나도
없고 전부 검색 문제입니다. 그리고 원인이 하나로 모입니다.

색인은 두 층입니다. 코드표 항목은 짧고(1~2문장), 매뉴얼 본문 청크는
깁니다(최대 2,000자). 순수 유사도 순위로 자르면 **긴 본문 청크가 짧은
코드표 항목을 밀어내고 상위가 한 층으로 쏠립니다.**

```
Q11 "탈이온수 흐르는 게 막힌 것 같습니다"
  기대: M9E-3101 (DI flow - IC)
  실제: M9e#Lack_of_Flow#4, #2, ...   ← 전부 본문
```

`Lack of Flow` 는 틀린 결과가 아닙니다. 오히려 관련 챕터입니다. 다만
"무엇이 문제인가"(코드표)와 "어떻게 조치하는가"(본문)는 다른 질문이고,
정비원에게는 둘 다 필요합니다. Q05·Q07·Q13·Q36 도 같은 형태입니다.

기기 축도 같습니다. 계기 자체의 고장과 입력 카드·배선의 고장은 서로
다른 원인 계층인데, 계기 문서가 수백 청크로 많다는 이유만으로 카드
문서가 상위에서 사라집니다(Q16·Q32).

## 어떻게 고쳤나

순위를 바꾸지 않습니다. **상위 3건 안에 각 계층이 최소 1건씩 남도록**
자리 하나를 내줍니다. 1위는 어떤 경우에도 건드리지 않습니다.

확보 창을 3으로 둔 것은 시스템의 다른 부분과 맞추기 위해서입니다.
근거 충분성 채점기도 상위 3건만 보고, 화면도 상단 몇 건을 먼저
읽힙니다. 5번째 자리에 밀어 넣으면 규칙이 있으나 마나 합니다.

## 세 단계로 나눈 이유

```
COPILOT_DIVERSIFY = off | kind | all      (기본 kind)
```

- `off`  순수 유사도 순위 — 기존 동작
- `kind` 코드표·본문 두 층 확보
- `all`  위 + 계기·카드 두 기기 축까지 확보

`all` 을 기본으로 두지 않았습니다. 확인해 보니 "resin bed replace"
질의에서 무관한 카드 코드가 상위 3위로 올라와 정답을 밀어냈습니다.
기기 축 확보는 Q16·Q32 를 살릴 수 있지만 다른 문항을 죽일 수도
있습니다. **어느 쪽이 이득인지는 측정으로 정하십시오.**

## 측정 방법

hybrid 만 돌리면 구성당 2~3분입니다.

```cmd
set COPILOT_DIVERSIFY=off
python -m eval.run_eval_v2 --systems hybrid --md eval/sc_off.md

set COPILOT_DIVERSIFY=kind
python -m eval.run_eval_v2 --systems hybrid --md eval/sc_kind.md

set COPILOT_DIVERSIFY=all
python -m eval.run_eval_v2 --systems hybrid --md eval/sc_all.md
```

세 표의 syn / body / typo / abstain 행을 비교해 채택 값을 정하고,
그 값으로 4구성 전체를 다시 돌려 최종 스코어카드를 뽑으십시오.
어느 설정으로 측정했는지는 스코어카드 `실험 조건` 줄에
`diversify=kind` 형태로 자동 기록됩니다.

## 정직하게 밝힐 점

이 규칙은 **실패 문항을 분석해서 나왔습니다.** 다만 고친 대상은
"이 문항을 맞히는 로직"이 아니라 "상위 결과에 두 정보 계층이 모두
보여야 한다"는 구성 정책입니다. 특정 문항이나 특정 코드를 지목하지
않으며, 평가셋과 무관하게 사용자에게 이득입니다.

그래도 판정은 새 문항에서 나야 합니다. 도남진 님이 추가하신 문항에서
같은 경향이 유지되는지 확인하는 것이 이 개선의 진짜 검증입니다.

## 확인하지 못한 것

작업 환경에 임베딩이 없어 **lexical 로만 회귀 확인했습니다**(세 모드
모두 17/45 로 동일 — 렉시컬에서는 다양성 규칙이 발동할 여지가 거의
없습니다). hybrid·full 에서의 효과는 위 측정으로 직접 확인하셔야 합니다.

## 폐기한 접근

잡음 청크(`Modbus Map` 등)를 줄 길이로 걸러내려 했으나 폐기했습니다.
`Pin assignment` 청크의 평균 줄 길이가 8.5 로 `Modbus Map`(12~16)보다
**낮습니다.** 그 기준으로 거르면 Q32 가 원하는 청크가 먼저 죽습니다.
표 형식이라는 이유로 문서를 버리면 안 된다는 뜻입니다.
